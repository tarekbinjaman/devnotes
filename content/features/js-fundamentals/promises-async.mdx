## What it is

A **Promise** is an object representing a value that will be available later. It is always in one of three states:

| State | Meaning | Transitions to |
| --- | --- | --- |
| `pending` | still working | fulfilled or rejected |
| `fulfilled` | finished with a value | (final) |
| `rejected` | failed with a reason | (final) |

Once settled, a promise **never changes** again. `async/await` is syntax on top of promises: an `async` function always returns a promise, and `await` pauses the function until a promise settles, letting you write async code that reads top to bottom with normal `try/catch`.

| Combinator | Resolves when | Rejects when |
| --- | --- | --- |
| `Promise.all` | **all** fulfill (array of values) | the **first** rejection |
| `Promise.allSettled` | all settle (array of `{ status, value / reason }`) | never |
| `Promise.race` | the **first to settle** fulfills | the first to settle rejects |
| `Promise.any` | the **first to fulfill** | all reject (`AggregateError`) |

## Common mistake vs correct

<CodeTabs>
<Tab label="Common mistake">

```ts
// ❌ Sequential awaits for independent requests: total time = sum
const user = await fetchUser(id);       // 300 ms
const orders = await fetchOrders(id);   // 300 ms
const prefs = await fetchPrefs(id);     // 300 ms  → ~900 ms

// ❌ forEach does not wait for async callbacks
items.forEach(async (item) => { await save(item); });
console.log("all saved"); // runs before any save finishes

// ❌ Forgetting to return inside .then breaks the chain
getUser().then((u) => { getOrders(u.id); }).then((orders) => render(orders)); // orders is undefined

// ❌ fetch only rejects on network failure, not on 404/500
const data = await fetch("/api/user").then((r) => r.json());
```

</Tab>
<Tab label="Correct">

```ts
// ✅ Start independent work together: total time = slowest
const [user, orders, prefs] = await Promise.all([
  fetchUser(id),
  fetchOrders(id),
  fetchPrefs(id),
]); // ~300 ms

// ✅ Wait for all items (parallel) or use for...of (sequential)
await Promise.all(items.map((item) => save(item)));
for (const item of items) await save(item); // when order matters or the API is rate-limited

// ✅ Return the promise to keep the chain flat
getUser().then((u) => getOrders(u.id)).then((orders) => render(orders));

// ✅ Check response.ok
const res = await fetch("/api/user");
if (!res.ok) throw new Error(`HTTP ${res.status}`);
const data = await res.json();
```

</Tab>
</CodeTabs>

<Callout type="why" title="Why it matters">
- A promise starts its work when it is **created**, not when awaited. Creating them all first and awaiting together runs them in parallel.
- `forEach` ignores the promises its callback returns. `for...of` with `await` or `Promise.all(map(...))` actually waits.
- `.then` returns a **new** promise resolved with whatever the callback returns. Return nothing and the next step gets `undefined`.
- An unhandled rejection is reported globally and can crash a Node process. Every chain needs a `catch` somewhere.
</Callout>

## How it works

```text
fetchUser()  ──► pending ──┬──► fulfilled(value) ──► .then(onFulfilled) callbacks queued as microtasks
                           └──► rejected(reason) ──► .catch / .then(_, onRejected)
```

- `.then(f)` returns a new promise. If `f` returns a value, the new promise fulfills with it. If `f` returns a promise, the chain **waits** for it. If `f` throws, the new promise rejects.
- A rejection skips every `.then` until it reaches a `.catch`. After `.catch` returns a value, the chain is **fulfilled** again.
- `await p` is roughly `p.then(rest-of-function)`. A rejected `p` makes `await` **throw**, so `try/catch` works.
- Callbacks always run asynchronously as microtasks, even for an already-resolved promise (see [The Event Loop](/js-fundamentals/event-loop)).

## Use-case demos

### Use case 1: cancel stale requests with AbortController

```tsx
function useUser(id: string) {
  const [user, setUser] = useState<User | null>(null);
  const [error, setError] = useState<Error | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    fetch(`/api/users/${id}`, { signal: controller.signal })
      .then((r) => {
        if (!r.ok) throw new Error(`HTTP ${r.status}`);
        return r.json();
      })
      .then(setUser)
      .catch((e) => {
        if (e.name !== "AbortError") setError(e); // aborts are expected, not errors
      });
    return () => controller.abort(); // id changed or unmounted: drop the old request
  }, [id]);

  return { user, error };
}
```

This prevents a slow response for an old `id` from overwriting the newer one (a race condition).

### Use case 2: timeout and retry helpers

```ts
function withTimeout<T>(promise: Promise<T>, ms: number): Promise<T> {
  let timer: ReturnType<typeof setTimeout>;
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error(`Timed out after ${ms} ms`)), ms);
  });
  return Promise.race([promise, timeout]).finally(() => clearTimeout(timer));
}

async function retry<T>(fn: () => Promise<T>, attempts = 3, baseDelay = 200): Promise<T> {
  for (let i = 0; ; i++) {
    try {
      return await fn(); // `return await` so the catch below sees the rejection
    } catch (err) {
      if (i >= attempts - 1) throw err;
      await new Promise((r) => setTimeout(r, baseDelay * 2 ** i)); // 200, 400, 800 ...
    }
  }
}

const data = await retry(() => withTimeout(fetch("/api/report").then((r) => r.json()), 5000));
```

For `fetch`, `AbortSignal.timeout(5000)` passed as `signal` also cancels the underlying request, which `Promise.race` does not.

### Use case 3: dashboard widgets that fail independently

```ts
const results = await Promise.allSettled([fetchSales(), fetchTraffic(), fetchTickets()]);

const [sales, traffic, tickets] = results.map((r) =>
  r.status === "fulfilled" ? { data: r.value } : { error: String(r.reason) },
);
// One failing API shows an error card instead of breaking the whole page
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- **Unbounded parallelism**: `Promise.all(10_000 urls)` fires 10,000 requests at once. Batch them or use a concurrency limit.
- `Promise.all` rejects fast but **does not cancel** the other promises; they keep running. Use an `AbortController` if you need to stop them.
- `return promise` vs `return await promise` inside `try`: only `return await` lets that `try/catch` handle the rejection.
- `useEffect(async () => ...)` is invalid: the effect must return a cleanup function, not a promise. Define an async function inside and call it.
- Don't wrap a promise in `new Promise` (the "explicit construction" anti-pattern). Just return or chain the existing promise.
</Callout>

## Interview questions

<QA q="What does this promise chain print?" level="junior">

```js
Promise.resolve(1)
  .then(() => { throw new Error('boom'); })
  .then(() => console.log('skipped'))
  .catch((e) => { console.log('caught', e.message); return 2; })
  .then((v) => console.log('after', v));
```

Output:

```text
caught boom
after 2
```

The throw rejects the promise returned by the first `.then`, so the second `.then` is skipped. `.catch` handles it and returns `2`, which **fulfills** the chain again, so the last `.then` runs with `2`.

</QA>

<QA q="What does this code print and in what order?" level="mid">

```js
const wait = (ms) => new Promise((r) => setTimeout(r, ms));
async function run() {
  [3, 1, 2].forEach(async (n) => {
    await wait(n * 10);
    console.log(n);
  });
  console.log('done');
}
run();
```

Output:

```text
done
1
2
3
```

`forEach` calls each async callback and ignores the returned promise, so `done` prints immediately. The three waits run **in parallel** and finish after 10, 20 and 30 ms, so the numbers print in order of delay, not array order. Use `for...of` with `await` for sequential execution, or `await Promise.all(arr.map(...))` to wait for all.

</QA>

<QA q="What do these combinators log?" level="mid">

```js
const fail = (ms, v) => new Promise((_, rej) => setTimeout(() => rej(new Error(v)), ms));
const ok = (ms, v) => new Promise((res) => setTimeout(() => res(v), ms));

Promise.race([fail(10, 'fast-fail'), ok(20, 'slow-ok')])
  .then(console.log, (e) => console.log('race:', e.message));
Promise.any([fail(10, 'fast-fail'), ok(20, 'slow-ok')])
  .then((v) => console.log('any:', v));
```

Output:

```text
race: fast-fail
any: slow-ok
```

`race` settles with the first promise to **settle**, which is the rejection at 10 ms. `any` ignores rejections and resolves with the first promise to **fulfill**, the one at 20 ms. `any` only rejects (with an `AggregateError`) if every input rejects.

</QA>

<QA q='What are the three states of a promise?' level="junior">

`pending`, `fulfilled` and `rejected`. A promise starts pending and settles exactly once, either fulfilled with a value or rejected with a reason. After settling it is immutable: calling `resolve` or `reject` again does nothing.

</QA>

<QA q='When would you use Promise.allSettled instead of Promise.all?' level="mid">

Use `Promise.all` when you need **every** result and one failure makes the whole operation useless (for example, data needed to render a single form). Use `Promise.allSettled` when the tasks are **independent** and you want each outcome, such as dashboard widgets or a bulk upload where you report which files failed. `allSettled` never rejects; you inspect each `status`.

</QA>

<QA q='How do you run awaits in parallel instead of sequentially?' level="junior">

Start the promises first, then await them together:

```ts
const [a, b] = await Promise.all([getA(), getB()]);
```

Writing `const a = await getA(); const b = await getB();` waits for `getA` to finish before `getB` even starts. Only keep them sequential when the second call depends on the first result.

</QA>

<QA q='How would you cancel a fetch request, for example when a React component unmounts?' level="mid">

Create an `AbortController`, pass `controller.signal` to `fetch`, and call `controller.abort()` in the effect cleanup. The fetch promise rejects with an `AbortError` (a `DOMException`), which you should ignore rather than show as an error. This also prevents a slow response for old props from overwriting newer data.

</QA>

<QA q='What is the difference between return promise and return await promise inside try/catch?' level="senior">

With `return promise`, the function returns immediately and the promise rejects **after** leaving the `try`, so the local `catch` never runs and the caller gets the rejection. With `return await promise`, the function waits inside the `try`, so a rejection throws there and the local `catch` (and `finally` timing) works as expected. Outside of `try` blocks the two are effectively the same.

</QA>

<QA q='How would you implement a concurrency limit for many async tasks?' level="senior">

Run a fixed number of workers that pull from a shared queue:

```ts
async function mapLimit<T, R>(items: T[], limit: number, fn: (x: T) => Promise<R>) {
  const results: R[] = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;
      results[i] = await fn(items[i]);
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}
```

Because JavaScript is single-threaded, `next++` is safe without locks. Results keep the input order because each worker writes to its own index.

</QA>
