## What it is

Showing a list (products, users, orders) with a search box and filters. With a few items anything works. With thousands of items, the naive version filters on **every render**, so typing in the box feels slow.

## Standard vs optimized

<CodeTabs>
<Tab label="Standard">

```tsx
function ProductList({ products }: { products: Product[] }) {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");

  // ❌ Runs on EVERY render, including unrelated state changes
  const visible = products.filter(
    (p) =>
      (category === "all" || p.category === category) &&
      p.name.toLowerCase().includes(query.toLowerCase()),
  );

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ul>
        {visible.map((p) => (
          <ProductRow key={p.id} product={p} />
        ))}
      </ul>
    </>
  );
}
```

</Tab>
<Tab label="Optimized">

```tsx
function ProductList({ products }: { products: Product[] }) {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");

  // ✅ Input updates instantly; the expensive list catches up a moment later
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;

  // ✅ Lower-case the searchable text once, not on every keystroke
  const indexed = useMemo(
    () => products.map((p) => ({ ...p, _search: p.name.toLowerCase() })),
    [products],
  );

  // ✅ Only re-filter when inputs actually change
  const visible = useMemo(() => {
    const q = deferredQuery.trim().toLowerCase();
    return indexed.filter(
      (p) => (category === "all" || p.category === category) && (!q || p._search.includes(q)),
    );
  }, [indexed, deferredQuery, category]);

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ul style={{ opacity: isStale ? 0.6 : 1 }}>
        {visible.map((p) => (
          <ProductRow key={p.id} product={p} />
        ))}
      </ul>
    </>
  );
}

// ✅ Rows don't re-render if their product didn't change
const ProductRow = memo(function ProductRow({ product }: { product: Product }) {
  return <li>{product.name}</li>;
});
```

</Tab>
</CodeTabs>

<Callout type="why" title="Why it's faster">
- **`useDeferredValue`** (React 18+) lets React render the input first and the big list in the background, so typing never freezes.
- **`useMemo`** caches the filtered result and only recomputes when `query`, `category` or `products` change.
- **`React.memo`** on the row skips re-rendering rows whose props are unchanged.
- Pre-computing the lower-cased text cuts work per keystroke.
</Callout>

## How to use

1. Keep the raw input value in state (`query`) so the input stays controlled and instant.
2. Wrap it with `useDeferredValue(query)` and filter using the deferred value.
3. Put the filter in `useMemo` with exactly the values it reads as dependencies.
4. Wrap list rows with `memo` and give them stable `key`s (database ids, not array index).
5. Over ~5,000 visible rows? Combine with a [virtualized list](/css/virtualized-list).

## Use-case demos

### Use case 1: e-commerce filters (category + price + search)

```tsx
type Filters = { q: string; category: string; maxPrice: number; inStock: boolean };

function useFilteredProducts(products: Product[], filters: Filters) {
  const q = useDeferredValue(filters.q).toLowerCase();
  return useMemo(
    () =>
      products.filter(
        (p) =>
          (filters.category === "all" || p.category === filters.category) &&
          p.price <= filters.maxPrice &&
          (!filters.inStock || p.stock > 0) &&
          p.name.toLowerCase().includes(q),
      ),
    [products, q, filters.category, filters.maxPrice, filters.inStock],
  );
}
```

### Use case 2: keep filters in the URL (shareable links)

```tsx
"use client";
import { useRouter, useSearchParams } from "next/navigation";

export function useUrlFilter(key: string) {
  const params = useSearchParams();
  const router = useRouter();
  const value = params.get(key) ?? "";
  const setValue = (v: string) => {
    const next = new URLSearchParams(params);
    v ? next.set(key, v) : next.delete(key);
    router.replace(`?${next}`, { scroll: false });
  };
  return [value, setValue] as const;
}

// const [q, setQ] = useUrlFilter("q");
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- Don't `useMemo` tiny lists (under ~100 items): the overhead isn't worth it.
- Inline objects/functions passed to memoized rows (`onClick={() => ...}`) break `memo`. Use `useCallback`.
- If the data lives on the server and is large (10k+ rows), filter **on the server** instead. See [Server-side filtering & pagination](/backend/server-filtering-pagination).
</Callout>

## Interview questions

<QA q="Should the filtered list be stored in state?" level="junior">

No. The filtered list can be computed from the full list and the filter values, so store only the inputs (the list and the query) and derive the result during render. Storing it separately means keeping two pieces of state in sync, which leads to bugs when one is updated and the other isn't. If the computation is expensive, memoize it with [useMemo](/fundamentals/use-memo).

</QA>

<QA q="The input lags when typing in a filter box over 5,000 items. How do you debug and fix it?" level="mid">

Profile with React DevTools to see whether the time goes to the filter calculation or to rendering the rows. Then, depending on the cause: memoize the filtering with `useMemo`; wrap rows in `memo` with stable props so unchanged rows skip rendering; use `useDeferredValue(query)` so the input updates immediately and the list re-renders in the background; and [virtualize](/css/virtualized-list) the list so only visible rows are in the DOM. If the data is much larger or lives on the server, filter on the server.

</QA>

<QA q="How does useDeferredValue work?" level="mid">

`const deferredQuery = useDeferredValue(query)` returns the old value during the urgent render, so the input updates right away, then React re-renders in the background with the new value. That background render is interruptible: if the user types again, React abandons it and starts over with the latest value. It only helps if the slow component re-renders based on the deferred value and is memoized (or its work is in `useMemo`), otherwise it re-renders with the urgent update anyway. You can compare `query !== deferredQuery` to show a 'stale' style while it catches up.

</QA>

<QA q="useDeferredValue vs useTransition?" level="senior">

Both mark work as non-urgent. `useTransition` wraps the **state update** (`startTransition(() => setFilter(x))`), so you need access to the setter; it gives you an `isPending` flag. `useDeferredValue` wraps a **value**, which is handy when the value comes from props or you don't control the update. Note you can't use a transition for a controlled input's own value, since typing must be urgent: keep the input state urgent and defer the expensive derived part.

</QA>

<QA q="How do you keep filters in the URL, and why would you?" level="mid">

Store filters in query parameters (`?category=shoes&maxPrice=100`) and read them as the source of truth, for example with `useSearchParams` in Next.js, updating with `router.replace` to avoid filling the history with every keystroke. Benefits: links are shareable and bookmarkable, filters survive refresh, and back/forward navigation works. Validate and parse the params because users can edit the URL.

</QA>

<QA q="When should filtering move to the server?" level="senior">

When the dataset is too large to send to the browser (tens of thousands of rows or more), when it changes often, or when users shouldn't receive all of it for security reasons. Client-side filtering is great for small to medium datasets already loaded, because it's instant. Server-side filtering with pagination and proper indexes scales but adds latency per change, so you debounce the requests. See [Server-side filtering & pagination](/backend/server-filtering-pagination).

</QA>

<QA q="What's wrong with this code?" level="junior">

```tsx
const [query, setQuery] = useState("");
const [filtered, setFiltered] = useState(items);
useEffect(() => {
  setFiltered(items.filter((i) => i.name.includes(query)));
}, [query]);
```

The filtered list is redundant state, updated in an effect: every keystroke renders twice (once with stale results), and because `items` is missing from the dependencies, new items never appear until the query changes. Compute it during render instead: `const filtered = useMemo(() => items.filter((i) => i.name.includes(query)), [items, query]);`. Searches are usually case-insensitive too, so lowercase both sides.

</QA>
