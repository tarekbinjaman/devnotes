## What it is

By default, every component you import goes into the page's JavaScript bundle, even a chart, map or rich-text editor the user may never open. **Code splitting** puts those in separate chunks that download only when rendered. **Lazy images** load only when they scroll into view.

## Standard vs optimized

<CodeTabs>
<Tab label="Standard">

```tsx
// ❌ The chart library (~200 KB) loads on first visit, even if hidden
import RevenueChart from "@/components/RevenueChart";
import MarkdownEditor from "@/components/MarkdownEditor";

export default function Dashboard() {
  const [showEditor, setShowEditor] = useState(false);
  return (
    <>
      <RevenueChart />
      <button onClick={() => setShowEditor(true)}>Write note</button>
      {showEditor && <MarkdownEditor />}
      <img src="/hero.jpg" />
    </>
  );
}
```

</Tab>
<Tab label="Optimized">

```tsx
import dynamic from "next/dynamic";
import Image from "next/image";

// ✅ Separate chunk, loaded when rendered; skeleton while loading
const RevenueChart = dynamic(() => import("@/components/RevenueChart"), {
  loading: () => <div className="h-64 animate-pulse rounded bg-zinc-200" />,
  ssr: false, // chart libs often need `window`
});
const MarkdownEditor = dynamic(() => import("@/components/MarkdownEditor"));

export default function Dashboard() {
  const [showEditor, setShowEditor] = useState(false);
  return (
    <>
      <RevenueChart />
      <button onClick={() => setShowEditor(true)}>Write note</button>
      {showEditor && <MarkdownEditor />}
      {/* ✅ Resized, modern format (AVIF/WebP), lazy by default, no layout shift */}
      <Image src="/hero.jpg" alt="Hero" width={1200} height={600} priority />
    </>
  );
}
```

</Tab>
<Tab label="Plain React (Vite)">

```tsx
import { lazy, Suspense } from "react";

const Settings = lazy(() => import("./pages/Settings"));

export function App() {
  return (
    <Suspense fallback={<Spinner />}>
      <Routes>
        <Route path="/settings" element={<Settings />} />
      </Routes>
    </Suspense>
  );
}
```

<Callout type="why" title="Why it's faster">
- **`next/dynamic` / `React.lazy`** split code at the import, so the first page load downloads less JS and becomes interactive sooner (better LCP/INP).
- **`next/image`** serves correctly sized, compressed images and lazy-loads anything below the fold.
- Use `priority` only on the **largest above-the-fold image** (your LCP element).
</Callout>

## How to use

1. Find big dependencies: run `npx @next/bundle-analyzer` (or check the build output sizes).
2. Wrap components that are heavy **and** not needed immediately (modals, charts, editors, maps) with `dynamic()`.
3. Give each one a `loading` skeleton with the same size, to avoid layout shift.
4. Replace `<img>` with `next/image`, always passing `width`/`height` (or `fill` + a sized parent).
5. Load heavy libraries inside event handlers when possible: `const { jsPDF } = await import("jspdf")`.

## Use-case demos

### Use case 1: load a library only when a button is clicked

```tsx
async function exportPdf(rows: Row[]) {
  const { default: jsPDF } = await import("jspdf"); // downloaded on first click only
  const doc = new jsPDF();
  rows.forEach((r, i) => doc.text(`${r.name}: ${r.total}`, 10, 10 + i * 8));
  doc.save("report.pdf");
}
```

### Use case 2: render a component only when it scrolls into view

```tsx
function LazyOnView({ children, height = 400 }: { children: React.ReactNode; height?: number }) {
  const ref = useRef<HTMLDivElement>(null);
  const [visible, setVisible] = useState(false);
  useEffect(() => {
    const io = new IntersectionObserver(([e]) => e.isIntersecting && (setVisible(true), io.disconnect()), {
      rootMargin: "200px",
    });
    if (ref.current) io.observe(ref.current);
    return () => io.disconnect();
  }, []);
  return <div ref={ref} style={{ minHeight: height }}>{visible && children}</div>;
}

// <LazyOnView><CommentsSection /></LazyOnView>
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- Don't lazy-load what's visible on first paint (header, hero): that makes it **slower**.
- Too many tiny chunks cause a waterfall of requests. Split big things, not every button.
- `ssr: false` means no HTML for that part on the server, which is bad for SEO content.
</Callout>

## Interview questions

<QA q="What is code splitting, and why does it improve performance?" level="junior">

Code splitting breaks your JavaScript bundle into smaller chunks that load on demand instead of shipping everything up front. Less JavaScript on the initial load means less to download, parse and execute, which improves metrics like LCP and INP, especially on slow phones. Bundlers create a split point wherever you use a dynamic `import()`. Next.js already splits by route automatically.

</QA>

<QA q="How do React.lazy and Suspense work together?" level="junior">

`React.lazy(() => import('./Chart'))` returns a component whose code is loaded the first time it renders. While the chunk is loading, the component suspends, and the nearest `Suspense` boundary shows its `fallback` (a spinner or skeleton). Once loaded, React renders the real component and keeps the code cached. The imported module must have a default export (or you map a named export to `default`).

</QA>

<QA q="What should you lazy-load and what should you not?" level="mid">

Good candidates: heavy components not needed for first paint (charts, rich text editors, maps, modals, admin-only panels), big libraries used only after an interaction (PDF export, date libraries for a picker), and below-the-fold content. Don't lazy-load above-the-fold content like the header or hero: it delays the most important paint and can cause layout shift. Avoid splitting tiny components, which just adds requests.

</QA>

<QA q="next/dynamic vs React.lazy?" level="mid">

`next/dynamic` is Next.js's wrapper around `React.lazy` and `Suspense`. It adds a `loading` option and `ssr: false` to skip server rendering for components that only work in the browser (for example ones that use `window`). In the App Router, `ssr: false` is only allowed inside Client Components. Also note that Server Components are already not shipped as JavaScript, so lazy loading is mainly useful for heavy Client Components.

</QA>

<QA q="How do you avoid the lazy-loaded component appearing with a noticeable delay?" level="senior">

Preload the chunk before it's needed: call the dynamic `import()` on hover or focus of the button that opens the modal, or when the browser is idle. Use a skeleton fallback with the same dimensions to avoid layout shift. For content that scrolls into view, trigger loading slightly before it's visible with an `IntersectionObserver` `rootMargin`. And keep chunk boundaries meaningful so one interaction doesn't trigger a waterfall of small requests.

</QA>

<QA q="How do you handle a lazy chunk that fails to load?" level="senior">

A failed dynamic import (network error, or an old chunk deleted after a new deploy) throws during render, so wrap lazy components in an error boundary that shows a retry or a 'reload' message. A common fix for deploy-related failures is to reload the page once when a chunk load error occurs, since the new HTML points to the new chunks. Keeping old assets available for a while after deploy also helps.

</QA>

<QA q="How do you lazy-load images properly?" level="mid">

Use the native `loading='lazy'` attribute (or `next/image`, which is lazy by default) for below-the-fold images, and always give images dimensions or an `aspect-ratio` to prevent layout shift. Don't lazy-load the LCP image (usually the hero): load it eagerly and mark it high priority, for example with `fetchpriority='high'` on an `img`, or the preload/priority prop of `next/image` (check the name for your Next.js version).

</QA>
