## What it is

By default, when a parent re-renders, **all its children re-render**, even if their props are identical. `memo(Component)` makes React **compare the new props with the previous props** (shallowly, with `Object.is` for each prop). If they're all the same, React reuses the last result and skips the child.

```tsx
const ProductCard = memo(function ProductCard({ product }: { product: Product }) {
  return <div>{product.name}</div>;
});
```

It **avoids some** re-renders, not all: a memoized component still re-renders when **its own state** or **a context it uses** changes.

```tsx
function ProductGrid({ products }: { products: Product[] }) {
  const [now, setNow] = useState(Date.now());

  return <SlowCardUI product={product} />;
```

```tsx
// ✅ Cards only re-render when their `product` prop changes
const ProductCard = memo(function ProductCard({ product }: { product: Product }) {
  return <SlowCardUI product={product} />;
});

function ProductGrid({ products }: { products: Product[] }) {
  const [now, setNow] = useState(Date.now());
  // … same interval …
  return (
    <>
      <Clock time={now} />
      {products.map((p) => <ProductCard key={p.id} product={p} />)}
    </>
  );
}

// Even better here: move the clock state INTO <Clock /> so the grid never re-renders.
```

<Callout type="why" title="Why it's faster">
- A shallow prop comparison (a few `===` checks) is much cheaper than rendering a big subtree.
- It's most useful for components that are **slow to render** and **often re-rendered with the same props** (list rows, charts, cards).
- It only works if props are **stable**: primitives, or objects/functions kept stable with [useMemo](/fundamentals/use-memo) / [useCallback](/fundamentals/use-callback).
</Callout>

## How to use

1. Profile first (React DevTools Profiler) to find components that re-render often and slowly.
2. Wrap them: `export default memo(MyComponent)`.
3. Make their props stable: `useCallback` for functions, `useMemo` for objects/arrays, or pass primitives (`id` instead of `{ id }`).
4. Before reaching for `memo`, try **moving state down** or passing **children** (see [Rendering](/fundamentals/rendering)). It's often simpler.

## Use-case demos

### Use case 1: memo + useCallback for a list with actions

```tsx
const TodoItem = memo(function TodoItem({ todo, onToggle }: { todo: Todo; onToggle: (id: string) => void }) {
  return (
    <label>
      <input type="checkbox" checked={todo.done} onChange={() => onToggle(todo.id)} />
      {todo.text}
    </label>
  );
});

function TodoList({ todos, setTodos }: Props) {
  const onToggle = useCallback(
    (id: string) => setTodos((prev) => prev.map((t) => (t.id === id ? { ...t, done: !t.done } : t))),
    [setTodos],
  );
  return todos.map((t) => <TodoItem key={t.id} todo={t} onToggle={onToggle} />);
  // Toggling one todo re-renders only that item (others keep the same object)
}
```

### Use case 2: custom comparison (use rarely)

```tsx
const Chart = memo(
  function Chart({ points, title }: { points: Point[]; title: string }) {
    return <HeavyCanvasChart points={points} title={title} />;
  },
  // Only re-render if the number of points or the title changed
  (prev, next) => prev.title === next.title && prev.points.length === next.points.length,
);
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- **Inline props break memo**: `style={{ color: "red" }}`, `onClick={() => …}` and `items={list.filter(…)}` are new every render.
- `children` JSX is a new object every render, so memo on a component that takes `children` rarely helps.
- Don't wrap everything. Comparing props for cheap components costs more than just rendering them.
- A custom comparison that ignores props can show **stale UI**. Prefer stabilizing the props.
</Callout>

## Interview questions

<QA q="What does React.memo do?" level="junior">

`memo(Component)` returns a version of the component that skips re-rendering when its parent re-renders with the **same props**. React compares each prop with the previous one using `Object.is` (a shallow comparison). It does not stop re-renders caused by the component's own state or by a context it reads changing.

</QA>

<QA q="What's wrong with this code?" level="junior">

```tsx
const Row = memo(function Row({ item, onSelect }: RowProps) { /* ... */ });

function List({ items }: { items: Item[] }) {
  return items.map((item) => (
    <Row key={item.id} item={item} onSelect={() => select(item.id)} />
  ));
}
```

`onSelect` is a new arrow function on every render of `List`, so every `Row` sees a changed prop and re-renders: the `memo` does nothing. Pass a stable function, for example `const handleSelect = useCallback((id) => select(id), [])` and `onSelect={handleSelect}`, and let `Row` call it with its own `item.id`.

</QA>

<QA q="What is shallow comparison, and why does it matter here?" level="mid">

Shallow comparison checks each prop with `Object.is`: primitives are equal if their values match, but objects, arrays and functions are equal only if they're the **same reference**. Two objects with identical contents created on different renders are not equal. That's why `memo` needs to be paired with `useMemo`/`useCallback` (or values defined outside the component) for any non-primitive prop.

</QA>

<QA q="Why not wrap every component in memo?" level="mid">

Comparing props has a cost on every render, and for cheap components it's often more than just re-rendering them. Many components receive new objects, functions or `children` every time, so memo would never actually skip anything. It also adds noise and makes it easy to get stale UI with custom comparators. Use it where profiling shows an expensive component re-rendering with the same props, such as large list rows or heavy charts.

</QA>

<QA q="What is the second argument to memo, and when should you use it?" level="senior">

`memo(Component, arePropsEqual)` lets you supply a custom comparison that returns `true` when the props are equal (skip the render). It's useful in rare cases, like comparing only an `id` and `updatedAt` instead of a big object. The risk: if you ignore a prop that actually affects output (including callbacks that close over new values), the component shows stale UI. Also, a deep equality check can be slower than re-rendering. Prefer stabilizing props instead.

</QA>

<QA q="Alternatives to memo for preventing expensive re-renders?" level="senior">

Move state down so the expensive component isn't under the state that changes, or lift the expensive part up and pass it as `children` to the component that re-renders often (its element doesn't change, so React skips it). Split contexts so the component doesn't subscribe to fast-changing values. And the React Compiler memoizes components and values automatically, which covers most cases where you'd reach for manual `memo`.

</QA>
