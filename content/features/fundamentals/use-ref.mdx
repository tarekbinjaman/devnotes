## What it is

`useRef` returns an object `{ current: value }` that **stays the same across renders**. Changing `ref.current` does **not** re-render the component.

Two main uses:
1. **Access a DOM element**: focus an input, measure size, scroll into view, integrate a non-React library.
2. **Remember a value** that the UI doesn't display: timer ids, previous values, "is mounted", the latest callback.

| | `useState` | `useRef` |
| --- | --- | --- |
| Survives re-renders | ✅ | ✅ |
| Changing it re-renders | ✅ | ❌ |
| Read it during render | ✅ | ❌ (avoid) |
| Good for | data shown in UI | DOM nodes, timers, instance values |

## Common mistake vs correct

<CodeTabs>
<Tab label="Common mistake">

```tsx
// ❌ document.querySelector in React: fragile, breaks with multiple instances
function Search() {
  useEffect(() => {
    (document.querySelector("#search") as HTMLInputElement).focus();
  }, []);
  return <input id="search" />;
}

// ❌ Timer id in a normal variable: lost on re-render, so you can't clear it
function Stopwatch() {
  let intervalId: number;
  const start = () => { intervalId = window.setInterval(tick, 1000); };
  const stop = () => clearInterval(intervalId); // undefined after a re-render
}

// ❌ Using a ref for UI data: screen doesn't update
const count = useRef(0);
<button onClick={() => count.current++}>{count.current}</button>
```

</Tab>
<Tab label="Correct">

```tsx
// ✅ DOM ref
function Search() {
  const inputRef = useRef<HTMLInputElement>(null);
  useEffect(() => inputRef.current?.focus(), []);
  return <input ref={inputRef} />;
}

// ✅ Mutable instance value that survives renders
function Stopwatch() {
  const [ms, setMs] = useState(0);
  const intervalRef = useRef<number | null>(null);

  const start = () => {
    if (intervalRef.current) return;
    intervalRef.current = window.setInterval(() => setMs((m) => m + 100), 100);
  };
  const stop = () => {
    if (intervalRef.current) clearInterval(intervalRef.current);
    intervalRef.current = null;
  };
  useEffect(() => stop, []); // clear on unmount

  return <>{(ms / 1000).toFixed(1)}s <button onClick={start}>Start</button><button onClick={stop}>Stop</button></>;
}

// ✅ UI data belongs in state
const [count, setCount] = useState(0);
<button onClick={() => setCount((c) => c + 1)}>{count}</button>
```

</Tab>
</CodeTabs>

<Callout type="why" title="Why use a ref">
- Refs give you a **direct, instance-safe** handle to DOM nodes, so there are no global selectors.
- Updating a ref costs **zero re-renders**. That's ideal for values that change often but aren't displayed.
- Refs keep their value across renders, unlike plain variables.
</Callout>

## How to use

1. `const ref = useRef<HTMLDivElement>(null)` and attach it with `<div ref={ref}>`.
2. Use `ref.current` in **effects and event handlers**, not during render.
3. Pass refs to your own components: in **React 19** `ref` is a normal prop. In React 18, wrap the component with `forwardRef`.
4. If changing the value should update the screen, use state instead.

## Use-case demos

### Use case 1: scroll to the newest chat message

```tsx
function ChatLog({ messages }: { messages: Message[] }) {
  const endRef = useRef<HTMLDivElement>(null);
  useEffect(() => {
    endRef.current?.scrollIntoView({ behavior: "smooth" });
  }, [messages.length]);
  return (
    <div className="h-96 overflow-y-auto">
      {messages.map((m) => <p key={m.id}>{m.text}</p>)}
      <div ref={endRef} />
    </div>
  );
}
```

### Use case 2: remember the previous value

```tsx
function usePrevious<T>(value: T) {
  const ref = useRef<T>();
  useEffect(() => { ref.current = value; }, [value]);
  return ref.current; // value from the previous render
}

const prevPrice = usePrevious(price);
// show ▲ or ▼ when price changes
```

### Use case 3: custom input that accepts a ref (React 19)

```tsx
function TextInput({ ref, ...props }: React.ComponentProps<"input">) {
  return <input ref={ref} className="rounded border px-3 py-2" {...props} />;
}

// React 18 version:
const TextInput18 = forwardRef<HTMLInputElement, React.ComponentProps<"input">>((props, ref) => (
  <input ref={ref} className="rounded border px-3 py-2" {...props} />
));
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- `ref.current` is `null` during the first render. DOM refs are set after commit.
- Don't read or write refs during render (except lazy init). It makes the output unpredictable.
- Refs aren't a way to avoid "too many re-renders". If the UI shows it, it's state.
</Callout>

## Interview questions

<QA q="What is the difference between useRef and useState?" level="junior">

Both keep a value between renders. Updating state with its setter triggers a re-render, and the value is a snapshot per render. A ref is a mutable object, `{ current: ... }`, that you can change at any time and changing it does **not** re-render. Rule of thumb: if the value is shown on screen, it's state; if it's bookkeeping the UI doesn't display (timer IDs, previous values, DOM nodes), it's a ref.

</QA>

<QA q="What are the two main use cases for useRef?" level="junior">

First, getting access to a DOM element: pass the ref to JSX (`ref={inputRef}`) and call `inputRef.current.focus()`, measure size, or scroll into view. Second, storing a mutable value that persists across renders without causing re-renders: interval IDs, a flag like 'has this already run', the previous value of a prop, or the latest callback for use inside a long-lived listener.

</QA>

<QA q="Why is ref.current null when I read it during the first render?" level="mid">

React attaches DOM refs during the **commit** phase, after rendering. During the first render the DOM node doesn't exist yet, so `ref.current` is still `null`. Read DOM refs in event handlers or effects, which run after commit. This is also why you shouldn't read or write refs during render: the value isn't tied to the render that's happening, so the output becomes unpredictable.

</QA>

<QA q="How do you pass a ref to your own component?" level="mid">

In React 19, `ref` is a regular prop for function components, so you accept `ref` in the props and forward it to the inner element. Before React 19 you had to wrap the component in `forwardRef`, which still works but is planned to be deprecated. If you want to expose only specific methods (like `focus` or `scrollToBottom`) instead of the raw DOM node, use `useImperativeHandle`.

</QA>

<QA q="What's wrong with this code?" level="mid">

```tsx
function Counter() {
  const count = useRef(0);
  return <button onClick={() => count.current++}>Clicked {count.current}</button>;
}
```

The value increments, but changing a ref doesn't trigger a re-render, so the button text stays at 0 until something else re-renders the component. Because the number is displayed, it must be state: `const [count, setCount] = useState(0)` and `setCount((c) => c + 1)`.

</QA>

<QA q="What is a callback ref and when is it useful?" level="senior">

Instead of a ref object you can pass a function to the `ref` attribute. React calls it with the DOM node when it's attached and (before React 19) with `null` when it's detached; in React 19 the function can also return a cleanup function. Callback refs are useful when you need to react to the node appearing, for example measuring it or attaching a `ResizeObserver`/`IntersectionObserver`, or when managing refs for a dynamic list of items (store nodes in a `Map` keyed by ID).

</QA>

<QA q="How do you implement a 'latest value' ref, and why is it useful?" level="senior">

Keep a ref that you update to the newest callback or value after each render (in an effect, for example `useLayoutEffect(() => { ref.current = callback })`), then read `ref.current` inside a long-lived subscription or interval. The subscription can be set up once and still always call the latest logic, without re-subscribing every time the callback changes. React's `useEffectEvent` hook is designed for this pattern; check that it's available in your React version before using it.

</QA>
