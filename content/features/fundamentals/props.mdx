## What it is

**Props** (properties) are the inputs of a component, like arguments to a function. A parent passes them, and the child reads them.

- Data flows **one way: down** (parent → child).
- Props are **read-only**. A child must never change them.
- When a parent re-renders with new props, the child re-renders with the new values.
- Anything can be a prop: strings, numbers, objects, arrays, **functions** (callbacks) and **JSX** (`children`).

## Common mistake vs correct

<CodeTabs>
<Tab label="Common mistake">

```tsx
// ❌ Mutating a prop
function PriceTag({ product }: { product: Product }) {
  product.price = product.price * 0.9; // changes the parent's object!
  return <span>${product.price}</span>;
}

// ❌ Copying a prop into state: it goes stale when the parent changes it
function Greeting({ name }: { name: string }) {
  const [displayName] = useState(name); // never updates after the first render
  return <h1>Hello {displayName}</h1>;
}

// ❌ Prop drilling through 4 levels that don't use it
<Page user={user} />  →  <Layout user={user} />  →  <Sidebar user={user} />  →  <Avatar user={user} />
```

</Tab>
<Tab label="Correct">

```tsx
// ✅ Typed props, defaults via destructuring, derive values instead of mutating
type PriceTagProps = {
  price: number;
  discount?: number;          // optional
  currency?: "USD" | "EUR";
};

function PriceTag({ price, discount = 0, currency = "USD" }: PriceTagProps) {
  const final = price * (1 - discount); // ✅ derived, nothing mutated
  return (
    <span>
      {new Intl.NumberFormat("en", { style: "currency", currency }).format(final)}
    </span>
  );
}

// ✅ Use the prop directly, no state copy
function Greeting({ name }: { name: string }) {
  return <h1>Hello {name}</h1>;
}

// ✅ Avoid drilling: pass the finished component down (composition)
<Layout sidebar={<Sidebar avatar={<Avatar user={user} />} />} />
```

</Tab>
</CodeTabs>

<Callout type="why" title="Why it works this way">
- **One-way data flow** makes bugs easy to trace: data has a single owner (whoever holds the state).
- **Read-only props** mean a child can't break its parent's data by accident.
- **Deriving** values during render keeps them in sync automatically, with no `useEffect` needed.
</Callout>

## How to use

1. Define a `Props` type for every component.
2. Destructure in the parameter list and set defaults there (`size = "md"`).
3. To let a child change data, pass a **callback** (`onChange`, `onSelect`) and keep the state in the parent.
4. Use `children` for content that goes inside a wrapper.
5. If you pass a prop through 3+ components that don't use it, consider **composition** or [Context](/fundamentals/context-api).

## Use-case demos

### Use case 1: controlled input (parent owns the value)

```tsx
type TextFieldProps = { label: string; value: string; onChange: (v: string) => void; error?: string };

function TextField({ label, value, onChange, error }: TextFieldProps) {
  return (
    <label className="block">
      <span>{label}</span>
      <input value={value} onChange={(e) => onChange(e.target.value)} aria-invalid={!!error} />
      {error && <small className="text-red-600">{error}</small>}
    </label>
  );
}

// Parent
const [email, setEmail] = useState("");
<TextField label="Email" value={email} onChange={setEmail} error={!email.includes("@") ? "Invalid email" : undefined} />
```

### Use case 2: reusable Button extending native props

```tsx
type ButtonProps = React.ComponentProps<"button"> & { variant?: "primary" | "ghost" };

function Button({ variant = "primary", className = "", ...rest }: ButtonProps) {
  const styles = variant === "primary" ? "bg-indigo-600 text-white" : "bg-transparent";
  return <button className={`rounded px-3 py-1.5 ${styles} ${className}`} {...rest} />;
}

<Button type="submit" disabled={saving} onClick={save}>Save</Button>
```

### Use case 3: resetting a child's state when a prop changes (use `key`)

```tsx
// Each user gets a fresh form; old typed values don't leak between users
<EditProfileForm key={user.id} user={user} />
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- `useState(prop)` only uses the prop on the **first** render. Use the prop directly, or reset with `key`.
- Spreading unknown props onto DOM elements (`{...props}`) can pass invalid attributes. Pick what you need.
- New object/function props every render (`style={{...}}`, `onClick={() => ...}`) break [React.memo](/fundamentals/react-memo). That's fine unless you're optimizing.
</Callout>

## Interview questions

<QA q="What is the difference between props and state?" level="junior">

Props are inputs passed **into** a component by its parent; the component must treat them as read-only. State is data a component **owns** and can change with its setter, which triggers a re-render. A simple way to explain it: props are like function arguments, state is like the component's memory. The same value is often state in a parent and a prop in its child.

</QA>

<QA q="Why are props read-only? What happens if you mutate them?" level="junior">

React's data flow is one-way: the parent owns the data and the child only describes UI from it. If a child mutates a prop object, React doesn't know anything changed (no setter was called), so the screen won't update reliably, and the parent's data is silently corrupted. Memoization (`memo`, `useMemo`) also breaks because it compares references. To change data, the child calls a callback prop and the owner updates its state.

</QA>

<QA q="What is prop drilling, and how do you avoid it?" level="mid">

Prop drilling is passing a prop through several intermediate components that don't use it, just to reach a deep child. It is not always bad, since it makes the data flow explicit. Fixes, in the order I'd try them: restructure with composition (pass the deep child as `children` so the middle layers don't need the prop), then [Context](/fundamentals/context-api) for widely needed values like theme or current user, and a state library (Zustand, Redux Toolkit) for complex shared state that changes often.

</QA>

<QA q="What's wrong with this code?" level="mid">

```tsx
function EditName({ initialName }: { initialName: string }) {
  const [name, setName] = useState(initialName);
  return <input value={name} onChange={(e) => setName(e.target.value)} />;
}
```

Nothing, as long as `initialName` really is just an initial value. The bug appears when the parent later passes a different `initialName` (say, the user picks another record): `useState` only reads its argument on the first render, so the input keeps showing the old name. Either make the component controlled (use the prop directly and call an `onChange` prop), or reset it by rendering `<EditName key={user.id} ... />` so a new `key` remounts it with fresh state.

</QA>

<QA q="What is the children prop and when would you use it?" level="junior">

`children` is whatever JSX you put between a component's opening and closing tags. It lets you build wrapper components (layouts, cards, modals, providers) that don't need to know what they render. It also helps performance: a wrapper that re-renders because of its own state doesn't re-render `children` that were created by its parent, because those elements didn't change.

</QA>

<QA q="What is the difference between a controlled and an uncontrolled input?" level="mid">

A controlled input gets its `value` from React state and reports changes through `onChange`, so React is the single source of truth: easy to validate, format or reset. An uncontrolled input keeps its own value in the DOM; you set a `defaultValue` and read it with a ref or from `FormData` on submit. Controlled is the default choice for interactive forms; uncontrolled is simpler for basic forms, file inputs, and React 19 form actions that read `FormData`.

</QA>

<QA q="How do you type props in TypeScript for a reusable Button that should accept all native button attributes?" level="senior">

Extend the native props type, for example `type ButtonProps = React.ComponentPropsWithoutRef<'button'> & ...` plus your own fields like `variant`. Destructure your custom props and spread the rest onto the `button`, so `onClick`, `disabled`, `type` and `aria-*` all work and are type-checked. Default `type` to `'button'` so it doesn't accidentally submit forms. In React 19 `ref` is a normal prop for function components, so you can use `ComponentPropsWithRef` instead of `forwardRef`.

</QA>
