## What it is

A **custom hook** is a function whose name starts with `use` and that calls other hooks. It lets you **reuse logic** (fetching, form handling, media queries, local storage) across components, the same way components let you reuse UI.

- Each component that calls the hook gets its **own independent state**. Hooks share *logic*, not *data*.
- The **Rules of Hooks** apply: call hooks only at the top level (not in loops/conditions), and only from components or other hooks.

<Tab label="With a custom hook">

```tsx
// hooks/useFetch.ts
export function useFetch<T>(url: string | null) {
  const [state, setState] = useState<{ data: T | null; loading: boolean; error: Error | null }>({
    data: null,
    loading: !!url,
    error: null,
  });

  useEffect(() => {
    if (!url) return;
    const controller = new AbortController();
    setState((s) => ({ ...s, loading: true, error: null }));
    fetch(url, { signal: controller.signal })
      .then((r) => {
        if (!r.ok) throw new Error(`HTTP ${r.status}`);
        return r.json() as Promise<T>;
      })
      .then((data) => setState({ data, loading: false, error: null }))
      .catch((error) => {
        if (error.name !== "AbortError") setState({ data: null, loading: false, error });
      });
    return () => controller.abort();
  }, [url]);

  return state;
}

// ✅ Components become short and focused on UI
function UserProfile({ id }: { id: string }) {
  const { data: user, loading, error } = useFetch<User>(`/api/users/${id}`);
  if (loading) return <Spinner />;
  if (error) return <ErrorMessage error={error} />;
  return <h1>{user!.name}</h1>;
}

function OrderList() {
  const { data: orders } = useFetch<Order[]>("/api/orders");
  // …
}
```

<Callout type="why" title="Why it's better">
- **Write once, fix once**: a bug fix (like adding `AbortController`) applies everywhere.
- **Components read like a description of the UI**, with no plumbing.
- **Testable in isolation** with `renderHook` from Testing Library.
- **Typed with generics**, so each caller gets the right data type.
</Callout>

## How to use

1. Spot repeated hook logic (the same `useState` + `useEffect` combo in 2+ places).
2. Move it into `hooks/useThing.ts`. The name **must** start with `use`.
3. Take inputs as parameters, and return what components need (value, setters, status) as an object or tuple.
4. Wrap returned functions in `useCallback` so consumers get stable references.
5. Keep hooks focused. Compose small hooks (`useDebounce` + `useFetch`) rather than one giant hook.

## Use-case demos

### Use case 1: `useMediaQuery` (responsive logic in JS)

```tsx
export function useMediaQuery(query: string) {
  const [matches, setMatches] = useState(false);
  useEffect(() => {
    const mql = window.matchMedia(query);
    const on = () => setMatches(mql.matches);
    on();
    mql.addEventListener("change", on);
    return () => mql.removeEventListener("change", on);
  }, [query]);
  return matches;
}

// const isMobile = useMediaQuery("(max-width: 640px)");
```

### Use case 2: `useForm` with validation

```tsx
export function useForm<T extends Record<string, string>>(initial: T, validate: (v: T) => Partial<Record<keyof T, string>>) {
  const [values, setValues] = useState(initial);
  const [touched, setTouched] = useState<Partial<Record<keyof T, boolean>>>({});
  const errors = validate(values); // derived, never stale

  const register = (name: keyof T) => ({
    name,
    value: values[name],
    onChange: (e: React.ChangeEvent<HTMLInputElement>) => setValues((v) => ({ ...v, [name]: e.target.value })),
    onBlur: () => setTouched((t) => ({ ...t, [name]: true })),
  });

  return { values, errors, touched, register, isValid: Object.keys(errors).length === 0 };
}

// const { register, errors, touched, isValid } = useForm({ email: "" }, (v) => (v.email.includes("@") ? {} : { email: "Invalid email" }));
// <input {...register("email")} />  {touched.email && errors.email}
```

### Use case 3: composing hooks (debounced search)

```tsx
function useSearch(query: string) {
  const debounced = useDebounce(query.trim(), 300);
  return useFetch<Result[]>(debounced ? `/api/search?q=${encodeURIComponent(debounced)}` : null);
}
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- A function that doesn't call any hooks shouldn't be named `use…`. Make it a normal utility.
- Hooks don't share state between components. For shared data, use [Context](/fundamentals/context-api) or a store.
- Never call hooks conditionally (`if (x) useFetch(…)`). Pass `null` to skip instead, like `useFetch(null)` above.
- For production data fetching, React Query/SWR are battle-tested `useFetch` replacements with caching.
</Callout>

## Interview questions

<QA q="What is a custom hook, and why are they named with 'use'?" level="junior">

A custom hook is a function whose name starts with `use` and that calls other hooks, so you can extract and reuse stateful logic (fetching, form handling, media queries) across components. The `use` prefix tells React's lint rules and the React Compiler that the function follows the Rules of Hooks, so they can check that it's called unconditionally at the top level. A function that doesn't call any hooks should be a normal utility without the prefix.

</QA>

<QA q="If two components use the same custom hook, do they share state?" level="junior">

No. Each call to a hook gets its own independent state, exactly as if each component had written the `useState` and `useEffect` calls itself. Custom hooks share **logic**, not state. To share data between components, lift it up, use [Context](/fundamentals/context-api), or use an external store (which you can wrap in a hook, such as with `useSyncExternalStore`).

</QA>

<QA q="What are the Rules of Hooks, and why do they exist?" level="mid">

Call hooks only at the top level of a component or custom hook (not inside conditions, loops, nested functions or after an early return) and only from React functions, not regular JavaScript functions. React identifies each hook by its **call order** within a component, so if the order changes between renders, state gets attached to the wrong hook. To 'skip' a hook conditionally, call it unconditionally and pass an argument that disables it, like `useFetch(null)`.

</QA>

<QA q="What's wrong with this code?" level="mid">

```tsx
function Profile({ userId }: { userId?: string }) {
  if (!userId) return null;
  const user = useUser(userId);
  return <h1>{user.name}</h1>;
}
```

The hook is called after an early return, so it runs on some renders and not others. When `userId` goes from undefined to a value, React sees a different number of hooks and throws an error. Call `useUser` before the return (with a hook that accepts an undefined or null id and does nothing), or render a child component that calls the hook only when `userId` exists.

</QA>

<QA q="How do you design a good custom hook API?" level="mid">

Give it a clear, specific purpose (`useOnlineStatus`, `useDebouncedValue`) rather than a generic lifecycle wrapper like `useMount`. Return an object for many values (easy to extend) or a tuple for a `useState`-like pair. Return stable functions with `useCallback` so callers can use them as dependencies, keep inputs minimal, type it with generics where data shape varies, and handle cleanup inside the hook so callers can't forget it.

</QA>

<QA q="Custom hooks vs higher-order components and render props?" level="senior">

All three reuse logic, but HOCs and render props wrap components, which leads to 'wrapper hell' in DevTools, prop name collisions, and unclear origins of props. Hooks compose as plain function calls inside a component, are easier to type in TypeScript, and make it obvious where each value comes from. HOCs and render props still appear in older libraries, but hooks are the default way to share stateful logic today.

</QA>

<QA q="How do you test a custom hook?" level="senior">

Use `renderHook` from React Testing Library, which renders the hook inside a test component and gives you `result.current`. Wrap state changes in `act`, and use `waitFor` for async updates. For data-fetching hooks, mock the network (MSW is common) instead of the hook's internals. Often the best test is through a real component that uses the hook, because that checks behavior rather than implementation.

</QA>
