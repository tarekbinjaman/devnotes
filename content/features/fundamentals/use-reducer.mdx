## What it is

`useReducer` is an alternative to `useState` for state with **many related fields** or **many ways to change**. You describe *what happened* (`dispatch({ type: "added", item })`), and a **reducer** function decides *how the state changes*.

```tsx
const [state, dispatch] = useReducer(reducer, initialState);

function reducer(state: State, action: Action): State {
  // pure: return a NEW state, never mutate
}
```

## Standard vs optimized

<CodeTabs>
<Tab label="Standard (many useState)">

```tsx
// ❌ 5 pieces of state that must change together: easy to forget one
function Checkout() {
  const [items, setItems] = useState<Item[]>([]);
  const [coupon, setCoupon] = useState<string | null>(null);
  const [status, setStatus] = useState<"idle" | "paying" | "done" | "error">("idle");
  const [error, setError] = useState<string | null>(null);
  const [orderId, setOrderId] = useState<string | null>(null);

  async function pay() {
    setStatus("paying");
    setError(null);
    try {
      const id = await api.pay(items, coupon);
      setOrderId(id);
      setStatus("done");
      setItems([]);           // forgot setCoupon(null)?
    } catch (e) {
      setStatus("error");
      setError(String(e));
    }
  }
}
```

</Tab>
<Tab label="With useReducer">

```tsx
type State = {
  items: Item[];
  coupon: string | null;
  status: "idle" | "paying" | "done" | "error";
  error: string | null;
  orderId: string | null;
};

type Action =
  | { type: "item_added"; item: Item }
  | { type: "item_removed"; id: string }
  | { type: "coupon_applied"; code: string }
  | { type: "pay_started" }
  | { type: "pay_succeeded"; orderId: string }
  | { type: "pay_failed"; error: string };

const initialState: State = { items: [], coupon: null, status: "idle", error: null, orderId: null };

function checkoutReducer(state: State, action: Action): State {
  switch (action.type) {
    case "item_added":
      return { ...state, items: [...state.items, action.item] };
    case "item_removed":
      return { ...state, items: state.items.filter((i) => i.id !== action.id) };
    case "coupon_applied":
      return { ...state, coupon: action.code };
    case "pay_started":
      return { ...state, status: "paying", error: null };
    case "pay_succeeded":
      // ✅ every related field updated in ONE place
      return { ...initialState, status: "done", orderId: action.orderId };
    case "pay_failed":
      return { ...state, status: "error", error: action.error };
  }
}

function Checkout() {
  const [state, dispatch] = useReducer(checkoutReducer, initialState);

  async function pay() {
    dispatch({ type: "pay_started" });
    try {
      dispatch({ type: "pay_succeeded", orderId: await api.pay(state.items, state.coupon) });
    } catch (e) {
      dispatch({ type: "pay_failed", error: String(e) });
    }
  }
}
```

</Tab>
</CodeTabs>

<Callout type="why" title="Why it's better">
- **All transitions in one pure function**: easy to read, impossible to "half update".
- **TypeScript discriminated unions** make TS check every action's payload.
- **Testable without React**: `expect(checkoutReducer(s, action)).toEqual(…)`.
- `dispatch` is **always stable**, so it's safe to pass down or put in Context without `useCallback`.
</Callout>

## How to use

1. Use it when several state values change together, or the next state depends on the previous in complex ways.
2. Name actions as **events** (`item_added`, `pay_failed`), not setters (`setItems`).
3. Keep the reducer **pure**: no API calls, no `Date.now()`, no mutations. Do side effects in handlers/effects, then dispatch.
4. Combine with [Context](/fundamentals/context-api) to share `state` + `dispatch` across a feature.

## Use-case demos

### Use case 1: reducer unit test

```ts
import { expect, test } from "vitest";

test("pay_succeeded clears the cart and stores the order id", () => {
  const s = { ...initialState, items: [item], coupon: "SAVE10", status: "paying" as const };
  const next = checkoutReducer(s, { type: "pay_succeeded", orderId: "o_1" });
  expect(next).toEqual({ ...initialState, status: "done", orderId: "o_1" });
});
```

### Use case 2: multi-step form wizard

```tsx
type WizardState = { step: 1 | 2 | 3; data: Partial<SignupData> };
type WizardAction =
  | { type: "next"; patch: Partial<SignupData> }
  | { type: "back" }
  | { type: "reset" };

function wizard(s: WizardState, a: WizardAction): WizardState {
  switch (a.type) {
    case "next": return { step: Math.min(s.step + 1, 3) as WizardState["step"], data: { ...s.data, ...a.patch } };
    case "back": return { ...s, step: Math.max(s.step - 1, 1) as WizardState["step"] };
    case "reset": return { step: 1, data: {} };
  }
}
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- For one or two independent values, `useState` is simpler.
- Mutating `state` inside the reducer (`state.items.push`) breaks re-rendering. Always return new objects.
- Side effects inside a reducer run twice in Strict Mode. Keep them out.
- App-wide complex state with many consumers may be better in **Zustand** or **Redux Toolkit**.
</Callout>

## Interview questions

<QA q="When would you choose useReducer over useState?" level="junior">

When state has several related values that change together, when the next state depends on the previous one in non-trivial ways, or when many different events update the same state (a form wizard, a cart, a data table with filters and paging). A reducer puts all the update logic in one pure function that's easy to read and test, and components just describe **what happened** by dispatching actions. For one or two independent values, `useState` is simpler.

</QA>

<QA q="What makes a reducer 'pure', and why does it matter?" level="junior">

A pure reducer computes the next state only from the current state and the action: no mutation of the old state, no API calls, no random values, no `Date.now()`. React may call it more than once (Strict Mode does in development), so side effects would run twice. Purity also makes reducers trivial to unit test: call it with a state and an action and assert on the result.

</QA>

<QA q="What's wrong with this reducer?" level="mid">

```ts
function reducer(state: State, action: Action) {
  switch (action.type) {
    case "added":
      state.items.push(action.item);
      return state;
  }
}
```

It mutates the existing state and returns the same reference, so React sees no change and may not re-render. It also has no default case, so unknown actions return `undefined`. Return a new object (`return { ...state, items: [...state.items, action.item] }`) and add a default that returns `state` or throws for unknown types.

</QA>

<QA q="How do you type actions in TypeScript?" level="mid">

Use a discriminated union, for example `type Action = { type: 'added'; item: Item } | { type: 'removed'; id: string }`. In each `case` of the `switch`, TypeScript narrows `action` so you can only access the payload that action has. Adding a `never` check in the default case makes the compiler complain when you add an action type but forget to handle it.

</QA>

<QA q="Where do side effects like API calls go when you use a reducer?" level="mid">

Outside the reducer: in event handlers or effects. A typical flow is: dispatch a 'fetch started' action, make the request in the handler or effect, then dispatch 'fetch succeeded' or 'fetch failed' with the result. The reducer only describes how state changes in response to each of those events. Libraries like Redux Toolkit add thunks for this, but the principle is the same.

</QA>

<QA q="useReducer + Context vs Redux Toolkit or Zustand: how do you choose?" level="senior">

`useReducer` plus Context is built in and good for state scoped to a feature or a moderately sized app. Its weakness is that every consumer of the state context re-renders on any change, because Context has no selectors. Redux Toolkit adds selectors, DevTools with time travel, middleware and RTK Query for server data; Zustand gives selector-based subscriptions with very little boilerplate. Pick the library when state is large, shared across the app and updated often, or when you need its tooling.

</QA>

<QA q="Why put dispatch in its own context?" level="senior">

`dispatch` from `useReducer` has a stable identity for the lifetime of the component. If you provide state and dispatch in separate contexts, components that only dispatch actions (buttons, forms) subscribe only to the dispatch context and never re-render when state changes. It's a cheap, effective way to reduce re-renders with the reducer + context pattern.

</QA>
