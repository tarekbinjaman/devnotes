## What it is

Every render creates **new function objects**. `() => {}` from render 1 is not `===` to `() => {}` from render 2. Usually that's fine. It matters when the function is:
- passed to a child wrapped in [`React.memo`](/fundamentals/react-memo) (a new function looks like a changed prop)
- used in a `useEffect` / `useMemo` dependency array
- returned from a custom hook that others depend on

`useCallback(fn, deps)` returns the **same function** until a dependency changes.

```tsx
const handleSelect = useCallback((id: string) => setSelected(id), []);
// same as: useMemo(() => (id: string) => setSelected(id), [])
```

## Standard vs optimized

<CodeTabs>
<Tab label="Standard">

```tsx
const Row = memo(function Row({ item, onDelete }: { item: Item; onDelete: (id: string) => void }) {
  return <li>{item.name} <button onClick={() => onDelete(item.id)}>×</button></li>;
});

function List({ items }: { items: Item[] }) {
  const [list, setList] = useState(items);
  const [filter, setFilter] = useState("");

  // ❌ New function every render → ALL memoized rows re-render on every keystroke
  const handleDelete = (id: string) => setList(list.filter((i) => i.id !== id));

  return (
    <>
      <input value={filter} onChange={(e) => setFilter(e.target.value)} />
      <ul>{list.map((i) => <Row key={i.id} item={i} onDelete={handleDelete} />)}</ul>
    </>
  );
}
```

</Tab>
<Tab label="Optimized">

```tsx
function List({ items }: { items: Item[] }) {
  const [list, setList] = useState(items);
  const [filter, setFilter] = useState("");

  // ✅ Stable reference; functional update means no dependency on `list`
  const handleDelete = useCallback((id: string) => {
    setList((prev) => prev.filter((i) => i.id !== id));
  }, []);

  return (
    <>
      <input value={filter} onChange={(e) => setFilter(e.target.value)} />
      {/* ✅ Rows skip re-rendering while typing */}
      <ul>{list.map((i) => <Row key={i.id} item={i} onDelete={handleDelete} />)}</ul>
    </>
  );
}
```

</Tab>
</CodeTabs>

<Callout type="why" title="Why it's faster">
- `React.memo` compares props with `===`. A stable callback makes it see "unchanged", so the child is skipped.
- **Functional updates** (`setList(prev => …)`) let you drop state from the deps, keeping the callback stable for longer.
- `useCallback` **on its own** doesn't make anything faster. It only helps together with `memo`, or with effect/memo dependencies.
</Callout>

## How to use

1. Use it when passing a function to a **`memo` child**, or when the function is a **dependency** of an effect/memo/another callback.
2. List every value the function reads in deps, or use functional updates to avoid them.
3. In custom hooks, wrap returned functions with `useCallback` so consumers get stable references.
4. With the React Compiler enabled, you can usually skip manual `useCallback`.

## Use-case demos

### Use case 1: function used inside an effect

```tsx
const fetchResults = useCallback(async () => {
  const res = await fetch(`/api/search?q=${encodeURIComponent(query)}&page=${page}`);
  setResults(await res.json());
}, [query, page]);

useEffect(() => {
  fetchResults();
}, [fetchResults]); // re-runs only when query or page changes
```

### Use case 2: custom hook returning stable actions

```tsx
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn((v) => !v), []);
  const setTrue = useCallback(() => setOn(true), []);
  const setFalse = useCallback(() => setOn(false), []);
  return { on, toggle, setTrue, setFalse };
}
```

### Use case 3: always-latest callback without changing identity

```tsx
// Stable function that always calls the newest `fn` (e.g. for event listeners)
function useEvent<A extends unknown[], R>(fn: (...a: A) => R) {
  const ref = useRef(fn);
  useLayoutEffect(() => { ref.current = fn; });
  return useCallback((...a: A) => ref.current(...a), []);
}
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- Wrapping every handler in `useCallback` adds noise and work with no gain if the child isn't memoized.
- Missing deps give **stale closures**: the function sees old state. Trust the exhaustive-deps lint rule.
- `onClick={() => handle(id)}` inside the memo child itself is fine. Stability matters for **props crossing into** memoized components.
</Callout>

## Interview questions

<QA q="What problem does useCallback solve? Explain it simply." level="junior">

Functions defined in a component are recreated on every render, so they're a new reference each time even if the code is identical. That's usually fine, but it breaks two things: a child wrapped in [React.memo](/fundamentals/react-memo) sees a 'changed' prop and re-renders anyway, and an effect that depends on the function re-runs every render. `useCallback(fn, deps)` returns the same function reference until a dependency changes.

</QA>

<QA q="Does useCallback make the function cheaper to create?" level="junior">

No. The inline function is still created on every render; `useCallback` just returns the cached one instead of the new one. So it doesn't save work by itself, and it adds a dependency comparison. Its only benefit is **referential stability**, which only matters if something compares the reference: a `memo` child, a hook dependency array, or a context value.

</QA>

<QA q="What's wrong with this code?" level="mid">

```tsx
const handleSave = useCallback(() => {
  api.save(draft);
}, []);
```

The dependency array is missing `draft`, so the function keeps the `draft` from the first render (a stale closure) and saves old data forever. Add `draft` to the dependencies; the exhaustive-deps lint rule catches this. If you want a stable function that still reads the latest value, use a functional state update or read from a ref instead of lying about dependencies.

</QA>

<QA q="I wrapped every handler in useCallback but the child still re-renders. Why?" level="mid">

`useCallback` only helps if the child is wrapped in `memo`; otherwise the child re-renders whenever the parent does, regardless of props. Even with `memo`, one unstable prop is enough to break it: an inline object (`style={{...}}`), an array from `.filter()`, or JSX passed as `children`. Use the React DevTools Profiler to see which prop changed, then stabilize that one.

</QA>

<QA q="How do you keep a callback stable when it depends on frequently changing state?" level="senior">

Options, from simplest: use a functional update (`setItems((prev) => [...prev, item])`) so the callback doesn't read the state at all and can have an empty dependency list; move the logic into a reducer and pass `dispatch`, which is always stable; or store the latest value in a ref and read `ref.current` in the callback. React's `useEffectEvent` is meant for functions called from effects that should see the latest values without re-triggering the effect, but it isn't a general replacement for passing callbacks to children.

</QA>

<QA q="Should custom hooks return functions wrapped in useCallback?" level="senior">

Generally yes for reusable hooks. Callers may put the returned functions into effect dependencies or pass them to memoized components, and an unstable function would cause re-renders or effect loops they can't fix from outside. react.dev recommends wrapping functions returned from custom hooks in `useCallback`. With the React Compiler this is handled automatically for compiled code.

</QA>

<QA q="When would you choose not to use useCallback at all?" level="senior">

When nothing compares the function's identity: handlers passed to plain DOM elements (`<button onClick>`) or to non-memoized children gain nothing. Adding it everywhere makes code harder to read and introduces stale-closure bugs when deps are wrong. Many teams only add it after profiling shows a problem, or rely on the React Compiler to do it automatically.

</QA>
