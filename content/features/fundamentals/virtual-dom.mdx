## What it is

The **virtual DOM** is a lightweight JavaScript description of the UI: plain objects like `{ type: "button", props: { children: "Save" } }`. JSX compiles to these objects.

On every render React:
1. Builds a **new** virtual tree from your components.
2. **Diffs** it against the previous tree (**reconciliation**).
3. Applies the **minimum** set of real DOM changes in the commit phase.

```text
State change → render() → new virtual tree ──┐
                                             ├─ diff → patch real DOM (only changed nodes)
               previous virtual tree ────────┘
```

### The diffing rules (why keys matter)

React uses two shortcuts to make diffing fast (O(n)):
1. **Different element type** (`<div>` → `<section>`, or `<Login>` → `<Dashboard>`) → React **destroys** the old subtree (state lost) and builds a new one.
2. **Same type at the same position** → React keeps the DOM node and component state, and only updates changed attributes.
3. **Lists** → React matches children by **`key`**. Without stable keys it matches by position.

## Common mistake vs correct

<CodeTabs>
<Tab label="Common mistake">

```tsx
// ❌ Index as key in a list that can be reordered/filtered/deleted
{todos.map((t, i) => (
  <li key={i}>
    <input defaultValue={t.text} />  {/* typed text jumps to the wrong row after delete */}
  </li>
))}

// ❌ Random keys: new key every render → every row is destroyed and re-created
{todos.map((t) => <TodoRow key={Math.random()} todo={t} />)}

// ❌ Changing the wrapper type conditionally resets all state inside
return isMobile ? <div><Editor /></div> : <section><Editor /></section>;
```

</Tab>
<Tab label="Correct">

```tsx
// ✅ Stable, unique key from the data
{todos.map((t) => (
  <li key={t.id}>
    <input defaultValue={t.text} />
  </li>
))}

// ✅ Keep the same element type; change only props/classes
return (
  <div className={isMobile ? "mobile" : "desktop"}>
    <Editor />   {/* same position + same type → state preserved */}
  </div>
);

// ✅ Use a key ON PURPOSE to reset a component
<ChatRoom key={roomId} roomId={roomId} />  // switching rooms gives a fresh component
```

</Tab>
</CodeTabs>

<Callout type="why" title="Why it's efficient">
- Comparing JS objects is much cheaper than touching the real DOM (layout and paint).
- **Stable keys** let React **move** existing DOM nodes instead of destroying and re-creating them, and keep each item's state attached to the right item.
- **Fiber** (React's engine) can split rendering into chunks and pause it for urgent updates like typing. That's what powers `useDeferredValue` and `useTransition`.
</Callout>

## How to use

1. Always give list items a `key` that is **stable** and **unique among siblings** (database id, slug).
2. Use index keys **only** for static lists that never reorder or change.
3. Keep the same element/component type at the same position to keep state.
4. Change `key` deliberately when you want a component to fully reset.

## Use-case demos

### Use case 1: what JSX actually becomes

```tsx
// You write:
<button className="btn" onClick={save}>Save</button>

// Compiles to (simplified):
jsx("button", { className: "btn", onClick: save, children: "Save" })

// Which returns a plain object (a virtual DOM node):
{ type: "button", props: { className: "btn", onClick: save, children: "Save" } }
```

### Use case 2: reset a form after successful submit

```tsx
const [formKey, setFormKey] = useState(0);

async function onSubmit(data: FormData) {
  await save(data);
  setFormKey((k) => k + 1); // new key → form remounts with empty fields
}

<ContactForm key={formKey} onSubmit={onSubmit} />
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- The virtual DOM isn't "faster than the DOM". It's a way to write declarative UI with **reasonably** minimal updates. Huge lists still need [virtualization](/css/virtualized-list).
- Duplicate keys cause warnings and wrong updates.
- Moving a component into a different parent element changes its position, so its state resets.
</Callout>

## Interview questions

<QA q="What is the virtual DOM? Explain it simply." level="junior">

It's a lightweight JavaScript description of the UI: plain objects (React elements) saying 'a `div` with this class containing this text'. When state changes, React builds a new description, compares it to the previous one, and applies only the differences to the real DOM. You write UI declaratively ('this is what it should look like') and React works out the imperative DOM updates.

</QA>

<QA q="Is the virtual DOM faster than the real DOM?" level="mid">

Not inherently. A hand-written, perfectly targeted DOM update will always beat building a tree and diffing it. The virtual DOM's value is that it gives **good enough** performance automatically while letting you write declarative code, and it avoids the common mistakes of manual DOM code (layout thrashing, unnecessary re-creation). Frameworks like Svelte and Solid show you can skip the virtual DOM entirely with compile-time or fine-grained reactivity, so it's a design trade-off, not a requirement.

</QA>

<QA q="What is reconciliation, and what assumptions make it fast?" level="mid">

Reconciliation is React's process of comparing the new element tree with the previous one to decide what to update. A general tree diff is O(n³), so React uses two heuristics to make it O(n): elements of **different types** produce entirely different trees (React tears down the old subtree and builds a new one), and **keys** identify which children in a list are the same item between renders. Same type at the same position means React keeps the DOM node and component state and just updates props.

</QA>

<QA q="Why shouldn't you use the array index as a key?" level="junior">

Keys tell React which item is which between renders. With index keys, inserting, removing or reordering items shifts every index, so React thinks item 0 is still item 0 and reuses its DOM node and state for a different item. Symptoms: input values or checkboxes ending up on the wrong row, wrong animations, extra work. Use a stable unique ID from the data. Index keys are acceptable only for static lists that never reorder or filter.

</QA>

<QA q="How can you use a key to reset a component's state on purpose?" level="mid">

Changing a component's `key` makes React treat it as a different component, so it unmounts the old one and mounts a fresh one with initial state. For example, `<ProfileForm key={userId} />` resets the form whenever you switch users, and changing a counter-based key after a successful submit clears a form. This is cleaner than an effect that manually resets several state variables when a prop changes.

</QA>

<QA q="What is React Fiber?" level="senior">

Fiber is the reconciliation engine introduced in React 16. Each component instance has a fiber node, a unit of work that React can process, pause, resume or throw away. That makes rendering **interruptible**, which enables concurrent features in React 18+: transitions (`startTransition`, `useTransition`), `useDeferredValue` and Suspense, where urgent updates like typing can interrupt a slow, non-urgent render. The commit to the DOM is still done in one synchronous step so the user never sees a half-updated UI.

</QA>

<QA q="What's wrong with this code?" level="senior">

```tsx
return isEditing ? (
  <div><Form /></div>
) : (
  <section><Form /></section>
);
```

The `Form` sits under a `div` in one branch and a `section` in the other. Because the parent element type changes, React throws away the whole subtree and remounts `Form`, losing its state (typed text, focus) every time `isEditing` toggles. Keep the same parent type and position (for example, toggle a class instead), or lift the form state up if it must survive the swap.

</QA>
