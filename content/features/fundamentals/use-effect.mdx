## What it is

`useEffect` lets a component **synchronize with something outside React**: fetching data, subscriptions, timers, event listeners, `document.title`, third-party widgets.

```tsx
useEffect(() => {
  // runs AFTER the render is committed to the screen
  return () => {
    // cleanup: runs before the next effect run and on unmount
  };
}, [dep1, dep2]); // re-run only when these change
```

| Dependency array | When the effect runs |
| --- | --- |
| *(none)* | After **every** render |
| `[]` | Once after mount (cleanup on unmount) |
| `[a, b]` | After mount, then whenever `a` or `b` changes |

## Common mistake vs correct

<CodeTabs>
<Tab label="Common mistake">

```tsx
// ❌ Missing dependency → uses stale userId forever
useEffect(() => {
  fetch(`/api/users/${userId}`).then((r) => r.json()).then(setUser);
}, []);

// ❌ No cleanup → listener leaks, and stacks up on every re-mount
useEffect(() => {
  window.addEventListener("resize", onResize);
}, []);

// ❌ Effect used to derive state → extra render + can get out of sync
const [fullName, setFullName] = useState("");
useEffect(() => {
  setFullName(`${first} ${last}`);
}, [first, last]);

// ❌ Object/function created during render as a dependency → runs every render
const options = { roomId };
useEffect(() => { connect(options); }, [options]);
```

</Tab>
<Tab label="Correct">

```tsx
// ✅ All used values in deps + abort outdated requests (no race conditions)
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/users/${userId}`, { signal: controller.signal })
    .then((r) => r.json())
    .then(setUser)
    .catch((e) => e.name !== "AbortError" && setError(e));
  return () => controller.abort();
}, [userId]);

// ✅ Always clean up subscriptions, listeners and timers
useEffect(() => {
  const onResize = () => setWidth(window.innerWidth);
  window.addEventListener("resize", onResize);
  return () => window.removeEventListener("resize", onResize);
}, []);

// ✅ No effect needed: derive during render
const fullName = `${first} ${last}`;

// ✅ Depend on primitives; create the object inside the effect
useEffect(() => {
  const conn = connect({ roomId });
  return () => conn.disconnect();
}, [roomId]);
```

</Tab>
</CodeTabs>

<Callout type="why" title="Why this is correct">
- **Complete dependencies** keep the effect in sync with the latest props and state (let the `react-hooks/exhaustive-deps` lint rule guide you).
- **Cleanup** prevents memory leaks, duplicate listeners and state updates after unmount.
- **AbortController** cancels outdated requests, so a slow old response can't overwrite new data.
- **Not using an effect** for derived data removes a whole render and a whole class of bugs.
</Callout>

## How to use

1. Ask first: **do I need an effect?** If you're transforming data for rendering, or responding to a user event, you don't. Compute during render, or do it in the event handler.
2. Put every reactive value the effect reads in the dependency array.
3. Return a cleanup for anything you start (listener, interval, subscription, request).
4. Need the latest value without re-running? Store it in a [ref](/fundamentals/use-ref).
5. Fetching in many places? Use **React Query / SWR**, or fetch in Next.js Server Components.

## Use-case demos

### Use case 1: interval timer with cleanup

```tsx
function Countdown({ seconds }: { seconds: number }) {
  const [left, setLeft] = useState(seconds);
  useEffect(() => {
    if (left <= 0) return;
    const id = setInterval(() => setLeft((s) => s - 1), 1000);
    return () => clearInterval(id);
  }, [left > 0]); // only re-subscribe when it starts/stops
  return <span>{left}s</span>;
}
```

### Use case 2: sync with document title / external API

```tsx
useEffect(() => {
  document.title = unread ? `(${unread}) Inbox` : "Inbox";
}, [unread]);
```

### Use case 3: close a dropdown when clicking outside

```tsx
function useClickOutside(ref: React.RefObject<HTMLElement>, onOutside: () => void) {
  useEffect(() => {
    const handler = (e: MouseEvent) => {
      if (ref.current && !ref.current.contains(e.target as Node)) onOutside();
    };
    document.addEventListener("mousedown", handler);
    return () => document.removeEventListener("mousedown", handler);
  }, [ref, onOutside]);
}
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- In development, Strict Mode runs effects **mount → cleanup → mount** to expose missing cleanups. Correct code works fine with this.
- Don't use effects to handle user events ("when the button is clicked, send…"). Do that in the click handler.
- Don't chain effects that set state that triggers other effects. Compute everything in one place.
- `async` can't be the effect function itself. Define an async function inside and call it.
</Callout>

## Interview questions

<QA q="What is the difference between no dependency array, an empty array, and an array with values?" level="junior">

With no array, the effect runs after **every** render. With `[]`, it runs once after the component mounts (and its cleanup runs on unmount). With `[a, b]`, it runs after mount and again after any render where `a` or `b` changed (compared with `Object.is`). The array isn't a choice you make freely: it must list every reactive value the effect reads, and the exhaustive-deps lint rule enforces that.

</QA>

<QA q="What is the cleanup function for, and when does it run?" level="junior">

The function you return from an effect undoes what the effect set up: clear an interval, remove an event listener, close a socket, abort a fetch. React runs it before the effect runs again with new dependencies, and when the component unmounts. Without it you get leaks, duplicate listeners, and updates from stale requests.

</QA>

<QA q="What's wrong with this code?" level="mid">

```tsx
const [fullName, setFullName] = useState("");
useEffect(() => {
  setFullName(first + " " + last);
}, [first, last]);
```

`fullName` is derived data, so it doesn't need state or an effect. This version renders once with a stale value, then sets state and renders again. Compute it during render: `const fullName = first + " " + last;`. If the calculation is expensive, wrap it in [useMemo](/fundamentals/use-memo). Effects are for syncing with systems **outside** React, not for transforming data.

</QA>

<QA q="How do you avoid race conditions when fetching data in an effect?" level="mid">

If the user changes the query quickly, an older request can resolve after a newer one and overwrite the correct results. In the cleanup, cancel the stale request with an `AbortController` (call `controller.abort()`), or set an `ignore` flag that the async code checks before calling `setState`. In real apps, React Query, SWR or a framework's data loading handle this (plus caching and deduplication) for you.

</QA>

<QA q="Why does my effect run twice in development?" level="mid">

In Strict Mode, React deliberately mounts, unmounts and remounts every component once in development to check that your effects clean up correctly. If running the effect twice causes a bug (two subscriptions, two analytics events), the cleanup is missing or incomplete. It doesn't happen in production. Don't 'fix' it with a ref that skips the second run; fix the cleanup.

</QA>

<QA q="useEffect vs useLayoutEffect: when do you need the layout version?" level="senior">

`useEffect` runs after the browser has painted, so it doesn't block the screen. `useLayoutEffect` runs synchronously after the DOM is updated but **before** paint. Use it only when you must measure the DOM and change something before the user sees it (for example positioning a tooltip based on its size), to avoid a visible flicker. It blocks painting, so prefer `useEffect` everywhere else.

</QA>

<QA q="When should you NOT use an effect?" level="senior">

The react.dev guide 'You Might Not Need an Effect' lists the common cases: transforming data for rendering (compute it during render), reacting to user events (do it in the event handler, since you know exactly what happened there), resetting state when a prop changes (use a `key`), and notifying a parent about a change (call the callback in the same handler). Chains of effects that set state to trigger other effects are a sign the logic should live in one place. Keep effects for synchronizing with external systems: subscriptions, timers, DOM APIs, non-React widgets, network connections.

</QA>

<QA q="An effect with an interval always logs count as 0. Why?" level="senior">

```tsx
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, []);
```

The effect captured `count` from the first render, and with `[]` it never re-runs, so the interval callback sees that stale closure forever. Fixes: add `count` to the dependencies (the interval is recreated when it changes), use a functional update like `setCount((c) => c + 1)` if you only need to update it, or read the latest value from a ref. The exhaustive-deps lint rule would have flagged this.

</QA>
