## What it is

**Rendering** means React calls your component function to find out what the UI should look like. It happens in two steps:

1. **Render phase**: React calls components and builds the new virtual tree (pure, no DOM changes).
2. **Commit phase**: React applies only the **differences** to the real DOM, then runs effects.

A component re-renders when:
- **Its state changes** (`setState` with a new value)
- **Its parent re-renders** (by default, all children re-render too, even with the same props)
- **A context it uses changes**

Props changing is **not** the trigger by itself. It's the parent re-rendering that passes them.

<Callout type="info" title="Re-render ≠ DOM update">
A re-render is just calling a function. If the output is the same, React doesn't touch the DOM. Re-renders are usually cheap. They only matter when a component is **slow** or renders **very often**.
</Callout>

## Common mistake vs correct

<CodeTabs>
<Tab label="Common mistake">

```tsx
// ❌ State at the top: typing re-renders the WHOLE page, including the slow chart
export default function Dashboard() {
  const [search, setSearch] = useState("");
  return (
    <>
      <input value={search} onChange={(e) => setSearch(e.target.value)} />
      <SearchResults query={search} />
      <ExpensiveChart />      {/* re-renders on every keystroke */}
      <BigTable />            {/* re-renders on every keystroke */}
    </>
  );
}

// ❌ Setting state during render → infinite loop
function Bad() {
  const [n, setN] = useState(0);
  setN(n + 1);
  return <p>{n}</p>;
}
```

</Tab>
<Tab label="Correct">

```tsx
// ✅ Move state down: only SearchSection re-renders while typing
function SearchSection() {
  const [search, setSearch] = useState("");
  return (
    <>
      <input value={search} onChange={(e) => setSearch(e.target.value)} />
      <SearchResults query={search} />
    </>
  );
}

export default function Dashboard() {
  return (
    <>
      <SearchSection />
      <ExpensiveChart />   {/* ✅ unaffected by typing */}
      <BigTable />
    </>
  );
}

// ✅ Or pass slow parts as children: they're created by the parent, so they don't re-render
function ScrollTracker({ children }: { children: React.ReactNode }) {
  const [y, setY] = useState(0);
  useEffect(() => {
    const on = () => setY(window.scrollY);
    window.addEventListener("scroll", on, { passive: true });
    return () => window.removeEventListener("scroll", on);
  }, []);
  return <div><ProgressBar y={y} />{children}</div>;
}

<ScrollTracker><ExpensiveChart /></ScrollTracker>
```

</Tab>
</CodeTabs>

<Callout type="why" title="Why this works">
- **Moving state down** shrinks the part of the tree that re-renders. This is the cheapest optimization, with no memoization needed.
- **`children` as props**: elements created by a parent that didn't re-render are the same objects, so React skips them.
- React 18+ **batches** multiple `setState` calls (even in timeouts and promises) into one re-render.
</Callout>

## How to use

1. Measure first: React DevTools → Profiler → record → see what rendered and how long it took.
2. Turn on **"Highlight updates when components render"** in DevTools settings to see re-renders live.
3. Fix in this order: **move state down** → **lift content up (children)** → [React.memo](/fundamentals/react-memo) / [useMemo](/fundamentals/use-memo) / [useCallback](/fundamentals/use-callback).
4. Split contexts so unrelated consumers don't re-render (see [Context API](/fundamentals/context-api)).

## Use-case demos

### Use case 1: see why something re-rendered (dev only)

```tsx
function useWhyDidYouRender(name: string, props: Record<string, unknown>) {
  const prev = useRef(props);
  useEffect(() => {
    const changed = Object.keys(props).filter((k) => !Object.is(prev.current[k], props[k]));
    if (changed.length) console.log(`[${name}] changed props:`, changed);
    prev.current = props;
  });
}
```

### Use case 2: keys control whether state is kept or reset

```tsx
// ✅ Stable ids: React keeps each row's state when the list re-orders
{items.map((i) => <Row key={i.id} item={i} />)}

// ❌ Index keys: after deleting item 0, row 1's input state "moves" to the wrong item
{items.map((i, idx) => <Row key={idx} item={i} />)}
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- Don't optimize re-renders you haven't measured. Most are fast.
- In development with Strict Mode, components render **twice** on purpose to catch impure code. Production renders once.
- Calling `setState` during render (outside a condition) causes an infinite loop.
</Callout>

## Interview questions

<QA q="What causes a component to re-render?" level="junior">

Three things: its own state changes, its parent re-renders, or a context it reads changes. A change in props alone is not a separate trigger, since props only change when the parent re-renders. Note that by default a parent's re-render re-renders **all** of its children, whether or not their props changed, unless a child is wrapped in [React.memo](/fundamentals/react-memo).

</QA>

<QA q="Does re-rendering mean React updates the DOM?" level="junior">

No. Rendering means React calls your component to get new JSX (the render phase). React then compares it with the previous result and, in the commit phase, touches only the DOM nodes that actually changed. A re-render with identical output produces no DOM changes, so it costs only the JavaScript work of running the component and diffing.

</QA>

<QA q="What are the render and commit phases?" level="mid">

In the **render phase** React calls components and computes what the UI should look like. This must be pure, because React can pause, restart or discard it in concurrent rendering. In the **commit phase** React applies the changes to the DOM, attaches refs, and then runs layout effects (synchronously, before paint) and later regular effects (after paint). That's why side effects go in effects or event handlers, never in the render body.

</QA>

<QA q="What is automatic batching?" level="mid">

Since React 18, multiple state updates in the same tick are grouped into a single re-render, whether they happen in an event handler, a `setTimeout`, a promise or a native event listener. Before React 18, only updates inside React event handlers were batched. If you really need to apply an update synchronously (for example to measure the DOM right after), `flushSync` from `react-dom` forces it, but that is rarely needed.

</QA>

<QA q="The page feels slow when typing in a form. How would you find out what is re-rendering?" level="mid">

Open React DevTools, turn on 'Highlight updates when components render', and type to see which parts flash. Then record with the **Profiler** tab with 'Record why each component rendered' enabled: it shows which components rendered, how long each took and why (state, props, context, parent). Typical fixes: move the input's state down into a smaller component so only it re-renders, pass expensive siblings as `children`, memoize a slow child with `memo`, or use `useDeferredValue` for an expensive result that depends on the input. Measure again after each change.

</QA>

<QA q="Why does my component render twice in development?" level="mid">

Strict Mode intentionally calls components (and initializers, reducers, `useMemo` callbacks) twice in development, and also runs effects mount, cleanup, mount. The goal is to expose impure rendering and missing effect cleanups. It doesn't happen in production builds, so don't 'fix' it by removing Strict Mode; fix the code that behaves differently when run twice.

</QA>

<QA q="How do you prevent unnecessary re-renders without memoizing everything?" level="senior">

Prefer structural fixes first: keep state as close as possible to where it's used (state colocation), pass stable subtrees as `children` so they don't re-render with the wrapper, split contexts so fast-changing values don't re-render everyone, and avoid storing derived values in state. Only then use `memo` plus `useMemo`/`useCallback` for components that are measurably slow. The React Compiler can add this memoization automatically, which reduces the need for manual tuning but doesn't fix a badly placed state.

</QA>
