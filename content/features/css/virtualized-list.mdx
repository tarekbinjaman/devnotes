## What it is

Every DOM element costs memory and layout time. 10,000 table rows = tens of thousands of elements, so scrolling stutters and the first render takes seconds. **Virtualization** (windowing) renders only the ~20 rows visible on screen plus a small buffer, and positions them inside a tall spacer so the scrollbar still looks right.

## Standard vs optimized

<CodeTabs>
<Tab label="Standard">

```tsx
// ❌ 50,000 <li> elements in the DOM
function LogList({ logs }: { logs: Log[] }) {
  return (
    <ul className="h-[600px] overflow-auto">
      {logs.map((l) => (
        <li key={l.id} className="h-9 border-b px-3">{l.message}</li>
      ))}
    </ul>
  );
}
```

</Tab>
<Tab label="Optimized">

```tsx
import { useVirtualizer } from "@tanstack/react-virtual";

function LogList({ logs }: { logs: Log[] }) {
  const parentRef = useRef<HTMLDivElement>(null);
  const v = useVirtualizer({
    count: logs.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 36, // row height in px
    overscan: 8,            // extra rows above/below for smooth scrolling
  });

  return (
    <div ref={parentRef} className="h-[600px] overflow-auto">
      {/* tall spacer = full list height */}
      <div style={{ height: v.getTotalSize(), position: "relative" }}>
        {v.getVirtualItems().map((row) => (
          <div
            key={logs[row.index].id}
            className="absolute left-0 top-0 h-9 w-full border-b px-3"
            style={{ transform: `translateY(${row.start}px)` }} // ✅ GPU-friendly positioning
          >
            {logs[row.index].message}
          </div>
        ))}
      </div>
    </div>
  );
}
```

<Callout type="why" title="Why it's faster">
- The DOM holds **~30 rows instead of 50,000**, so initial render and memory drop massively.
- **`transform: translateY`** moves rows without triggering layout, so scrolling stays at 60 fps.
- **`content-visibility: auto`** is a one-line CSS alternative where the browser skips rendering off-screen sections.
</Callout>

## How to use

1. `npm i @tanstack/react-virtual`
2. Give the scroll container a **fixed height** and `overflow: auto`.
3. Set `estimateSize` to your row height. For variable heights add `ref={v.measureElement}` and `data-index={row.index}` on each row.
4. Render the spacer (`getTotalSize()`) and absolutely position each visible row.
5. Combine with [List Filtering](/react/list-filtering): filter first, then virtualize the result.

## Use-case demos

### Use case 1: variable-height rows (chat messages)

```tsx
const v = useVirtualizer({
  count: messages.length,
  getScrollElement: () => parentRef.current,
  estimateSize: () => 80,
});

{v.getVirtualItems().map((row) => (
  <div
    key={row.key}
    data-index={row.index}
    ref={v.measureElement} // ✅ measures real height after render
    className="absolute left-0 w-full"
    style={{ transform: `translateY(${row.start}px)` }}
  >
    <Message msg={messages[row.index]} />
  </div>
))}
```

### Use case 2: virtualized grid of product cards

```tsx
const columns = 4;
const rowCount = Math.ceil(products.length / columns);
const v = useVirtualizer({ count: rowCount, getScrollElement: () => ref.current, estimateSize: () => 320 });

{v.getVirtualItems().map((row) => (
  <div key={row.key} className="absolute grid w-full grid-cols-4 gap-4"
       style={{ transform: `translateY(${row.start}px)` }}>
    {products.slice(row.index * columns, row.index * columns + columns).map((p) => (
      <ProductCard key={p.id} product={p} />
    ))}
  </div>
))}
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- Ctrl+F browser search can't find rows that aren't rendered.
- Under ~300 simple rows, virtualization adds complexity for no gain.
- Consider **pagination** or **server-side filtering** first. Do users really need 50k rows on one screen?
</Callout>

## Interview questions

<QA q="What is list virtualization, and how does it work?" level="junior">

Virtualization (or windowing) renders only the rows visible in the viewport, plus a small buffer (overscan), instead of all of them. A tall inner container keeps the scrollbar correct, and visible rows are positioned with `transform: translateY` based on the scroll offset. As the user scrolls, rows leaving the view are removed and new ones are rendered, so the DOM holds a few dozen nodes instead of 100,000.

</QA>

<QA q="Why is rendering 10,000 rows slow even if React is fast?" level="junior">

Each row creates DOM nodes, and the browser has to compute styles, lay out, and paint all of them, and keep them in memory. Initial render takes a long time, and every update to the list makes React reconcile 10,000 components. The cost is mostly in the browser's DOM and layout work, not just React, so the fix is to render fewer nodes.

</QA>

<QA q="What are the downsides of virtualization?" level="mid">

Browser find (Ctrl+F) can't find rows that aren't rendered. Accessibility needs care: screen readers only see rendered rows, so set `aria-rowcount` and `aria-rowindex` (or `aria-setsize`/`aria-posinset`) so the total is announced. Variable or dynamic row heights need measuring, and fast scrolling can show blank areas briefly. It also adds complexity, and features like sticky headers, keyboard navigation and scroll restoration take extra work.

</QA>

<QA q="How do you virtualize rows with variable heights, like chat messages?" level="mid">

Provide an `estimateSize` for unrendered rows, then measure each row's actual height after it renders (TanStack Virtual does this with `measureElement`, using a `ResizeObserver`) and update the position calculations. Expect small scroll adjustments as estimates are corrected, so good estimates help. For chat, you also need to keep scroll anchored to the bottom when new messages arrive and preserve position when older messages load above.

</QA>

<QA q="What is content-visibility: auto, and how does it compare to JS virtualization?" level="senior">

`content-visibility: auto` tells the browser to skip layout and paint for off-screen elements until they approach the viewport. Pair it with `contain-intrinsic-size` so skipped elements keep an estimated size and the scrollbar stays stable. Unlike JS virtualization, all elements stay in the DOM, so Ctrl+F and accessibility work, but DOM memory and React's rendering cost remain. It's a cheap win for long pages with a few hundred heavy sections, not for 100,000 rows.

</QA>

<QA q="Virtualization vs pagination vs infinite scroll: how do you choose?" level="senior">

Pagination is simplest, keeps URLs shareable ('page 3'), and works well for search results and admin tables. Infinite scroll suits feeds where users browse, but the DOM keeps growing, so it's often combined with virtualization, and it makes reaching the footer hard. Virtualization is for when users truly need one long scrollable list (logs, spreadsheets, chat). Often the best answer is less data: better filters and [server-side pagination](/backend/server-filtering-pagination).

</QA>

<QA q="A virtualized list shows blank rows when scrolling fast. What would you check?" level="senior">

Increase the overscan so more rows are rendered beyond the viewport. Make rows cheap to render: `memo` the row component, avoid heavy effects or images that block, and make sure keys are stable so rows aren't remounted. Check that size estimates are close to reality so positions don't jump. Profile to see if something else, like a scroll listener doing state updates on every event, is blocking the main thread.

</QA>
