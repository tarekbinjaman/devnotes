## What it is

The browser renders in stages: **Layout → Paint → Composite**. Animating `width`, `height`, `top`, `left` or `margin` re-runs **layout** every frame (slow, janky). Animating `transform` and `opacity` only touches the **composite** step, which the GPU handles.

## Standard vs optimized

<CodeTabs>
<Tab label="Standard">

```css
/* ❌ Triggers layout + paint every frame */
.drawer {
  position: fixed;
  left: -320px;
  width: 320px;
  transition: left 0.3s;
}
.drawer.open { left: 0; }

.card:hover {
  margin-top: -4px;          /* layout */
  box-shadow: 0 20px 40px #0003; /* expensive paint when animated */
  transition: all 0.3s;      /* animates everything, even unintended props */
}
```

</Tab>
<Tab label="Optimized">

```css
/* ✅ Compositor-only: transform + opacity */
.drawer {
  position: fixed;
  left: 0;
  width: 320px;
  transform: translateX(-100%);
  transition: transform 0.3s cubic-bezier(0.2, 0.8, 0.2, 1);
}
.drawer.open { transform: translateX(0); }

.card {
  position: relative;
  transition: transform 0.2s ease;
}
.card::after {
  /* pre-rendered shadow; we only fade its opacity */
  content: "";
  position: absolute;
  inset: 0;
  border-radius: inherit;
  box-shadow: 0 20px 40px #0003;
  opacity: 0;
  transition: opacity 0.2s ease;
  pointer-events: none;
}
.card:hover { transform: translateY(-4px); }
.card:hover::after { opacity: 1; }

/* ✅ Respect users who get motion sickness */
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after { transition-duration: 0.01ms !important; animation-duration: 0.01ms !important; }
}
```

</Tab>

```html
</aside>

<div class="transition-transform duration-200 hover:-translate-y-1 motion-reduce:transform-none">Card</div>
```

<Callout type="why" title="Why it's smoother">
- **`transform` / `opacity`** skip layout and paint, so they run on the GPU compositor even if JS is busy.
- Transition **specific properties**, not `all`, so you don't animate things by accident.
- **Fade a pre-made shadow** (`::after` opacity) instead of animating `box-shadow`.
- **`prefers-reduced-motion`** is an accessibility must.
</Callout>

## How to use

1. Replace position/size animations with `translate`, `scale` and `rotate`.
2. Replace show/hide with `opacity` (+ `visibility` or `pointer-events` when hidden).
3. Use `will-change: transform` **only** on elements about to animate (e.g. add on hover/open, remove after).
4. Check in Chrome DevTools → Rendering → "Paint flashing" (green flashes = repaints).

## Use-case demos

### Use case 1: modal enter animation

```css
.modal { opacity: 0; transform: scale(0.96) translateY(8px); transition: opacity .2s, transform .2s; }
.modal[data-open="true"] { opacity: 1; transform: none; }

/* Modern: animate from display:none (Chrome/Edge/Safari) */
dialog[open] { animation: pop .2s ease-out; }
@keyframes pop { from { opacity: 0; transform: scale(.96); } }
```

### Use case 2: animate height smoothly (accordion) without measuring

```css
/* ✅ grid-rows trick: animates 0fr → 1fr */
.accordion-body { display: grid; grid-template-rows: 0fr; transition: grid-template-rows .25s ease; }
.accordion[open] .accordion-body { grid-template-rows: 1fr; }
.accordion-body > div { overflow: hidden; }
```

### Use case 3: JS-controlled animation (Web Animations API)

```ts
el.animate(
  [{ transform: "translateX(0)" }, { transform: "translateX(-8px)" }, { transform: "translateX(8px)" }, { transform: "translateX(0)" }],
  { duration: 300, easing: "ease-in-out" },
); // shake on invalid input, no library needed
```

## Pitfalls & when not to use

<Callout type="warn" title="Watch out">
- `will-change` on many elements uses lots of GPU memory. Use it sparingly.
- `transform` creates a new stacking context, which can affect `z-index` and `position: fixed` children.
- Keep UI animations short: 150–300 ms.
</Callout>

## Interview questions

<QA q="Why are transform and opacity the cheapest properties to animate?" level="junior">

The browser renders in steps: style, layout, paint, composite. Changing `width`, `top` or `margin` triggers layout (recalculating positions of other elements) and paint on every frame. `transform` and `opacity` can usually be handled in the **composite** step alone: the element is already painted on its own layer, and the GPU just moves or fades it. That leaves more of each 16 ms frame budget free and keeps animations smooth.

</QA>

<QA q="What is layout thrashing, and how do you avoid it?" level="mid">

Layout thrashing is when JavaScript alternates reading layout values (`offsetHeight`, `getBoundingClientRect()`) and writing styles in a loop. Each read after a write forces the browser to recalculate layout synchronously, many times per frame. Avoid it by batching: do all reads first, then all writes, ideally inside `requestAnimationFrame`. Better still, animate with CSS transforms or the Web Animations API so you don't read layout every frame.

</QA>

<QA q="What does will-change do, and what's the risk of overusing it?" level="mid">

`will-change: transform` hints that an element is about to animate, so the browser can promote it to its own compositor layer ahead of time and avoid a jank spike at the start. Each layer uses GPU memory, so applying it to many elements (or permanently, like `* { will-change: transform }`) can make performance worse, especially on mobile. Apply it to a few elements that really animate, ideally just before the animation, and remove it afterwards.

</QA>

<QA q="A sidebar animation is janky on mobile. How would you debug it?" level="mid">

Record in the Chrome DevTools Performance panel (with CPU throttling) and look for long frames and purple 'Layout' or green 'Paint' work during the animation. Turn on 'Paint flashing' and the Layers panel in Rendering tools to see what's repainting. The usual cause is animating `left`, `width` or `margin`; switch to `transform: translateX(...)`. Also check for heavy `box-shadow` or `filter` animations, and JavaScript running on every frame.

</QA>

<QA q="How do you respect users who prefer reduced motion?" level="junior">

Use the `prefers-reduced-motion` media query: inside `@media (prefers-reduced-motion: reduce)`, remove or shorten large movements (parallax, slide-ins, auto-playing motion) and use simple fades or no animation instead. In JavaScript, check `window.matchMedia('(prefers-reduced-motion: reduce)').matches`. This is an accessibility issue: large motion can cause dizziness or nausea for people with vestibular disorders (WCAG 2.3.3).

</QA>

<QA q="CSS transitions vs CSS animations vs the Web Animations API vs a JS library?" level="senior">

Transitions animate between two states when a property changes (hover, class toggle) and are the simplest choice. `@keyframes` animations handle multi-step or looping motion without state changes. The Web Animations API (`element.animate()`) gives JavaScript control (play, pause, reverse, `finished` promise) while still running on the compositor for transform/opacity. Libraries like Motion add springs, gesture handling, and layout animations (FLIP) at the cost of bundle size. Pick the simplest one that meets the need.

</QA>

<QA q="How would you animate an element's height (like an accordion) smoothly?" level="senior">

Animating `height` triggers layout every frame, and you can't transition to `height: auto` with classic CSS. Options: animate a CSS grid row from `grid-template-rows: 0fr` to `1fr` (well supported and auto-sized); use `interpolate-size: allow-keywords` or `calc-size()` where supported to transition to `auto`; or use the FLIP technique: measure start and end sizes, then animate a `transform: scaleY` instead. For small content, the layout cost of the grid approach is usually fine.

</QA>
